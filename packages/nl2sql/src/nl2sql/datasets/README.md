# Demo datasets

Three small SQLite databases, packaged in the wheel and copied into the demo
project by `nl2sql setup --demo` and `nl2sql demo`. They are registered as
three separate datasources, so the demo shows the engine choosing between
datasources rather than always falling through to the only one.

| File | Datasource | Size | Origin |
| --- | --- | --- | --- |
| `chinook.sqlite` | `chinook` | ~1.0 MB | The Chinook sample database, vendored (MIT — see `THIRD_PARTY_NOTICES.md`) |
| `support.sqlite` | `support` | ~232 KiB | Synthetic, generated by this repository |
| `webanalytics.sqlite` | `webanalytics` | ~284 KiB | Synthetic, generated by this repository |

## Licence

`support.sqlite` and `webanalytics.sqlite` contain **synthetic data generated
by this repository**. No third-party dataset is used, downloaded or
redistributed in either, so nothing about them belongs in
`THIRD_PARTY_NOTICES.md`. Only `chinook.sqlite` is third-party.

The customer names and email addresses in the two generated databases are read
out of `chinook.sqlite` so the identities line up (see below); they are the
Chinook sample database's own fictional customers, not real people.

## Shared identities

Both generated databases carry a `customer_email` column, and a `customer_id`
that matches Chinook's `Customer.CustomerId`, so the same 59 people appear in
all three. That is what makes a question spanning two databases a real
question rather than a contrivance:

```sql
-- customers with an open ticket, and what they spent (needs chinook + support)
-- customers who viewed /pricing but never converted (needs chinook + webanalytics)
```

The engine plans each sub-query against a single datasource today, so those
cross-database questions are not yet answerable; the columns are in place for
when that lands.

All timestamps fall inside Chinook's invoice window, 2009-01-01 to 2013-12-22,
so the three line up in time.

## `support` — a customer support desk

| Table | Rows | Columns |
| --- | --- | --- |
| `agents` | 10 | `agent_id`, `full_name`, `email`, `team`, `hired_on` |
| `customers` | 59 | `customer_id`, `first_name`, `last_name`, `customer_email`, `country`, `city`, `signed_up_on` |
| `tickets` | 284 | `ticket_id`, `customer_id`, `customer_email`, `agent_id`, `subject`, `category`, `status`, `priority`, `opened_at`, `closed_at`, `satisfaction` |
| `ticket_messages` | 1125 | `message_id`, `ticket_id`, `sender_role`, `body`, `sent_at` |

`status` is one of `open`, `pending`, `escalated`, `resolved`, `closed`;
`priority` is `low`, `medium`, `high` or `urgent`. Resolved and closed tickets
have a `closed_at` after their `opened_at`; the rest have none.

## `webanalytics` — website traffic

| Table | Rows | Columns |
| --- | --- | --- |
| `devices` | 12 | `device_id`, `device_type`, `browser`, `operating_system` |
| `referrers` | 11 | `referrer_id`, `referrer_domain`, `channel` |
| `sessions` | 768 | `session_id`, `customer_id`, `customer_email`, `device_id`, `referrer_id`, `country`, `started_at`, `ended_at`, `duration_seconds`, `is_bounce` |
| `page_views` | 2455 | `page_view_id`, `session_id`, `page_path`, `page_title`, `viewed_at`, `seconds_on_page` |
| `conversions` | 83 | `conversion_id`, `session_id`, `customer_email`, `event_type`, `occurred_at`, `value_usd` |

`channel` is one of `direct`, `organic`, `paid`, `social`, `email`,
`referral`; `event_type` is `signup`, `trial_started`, `newsletter_signup` or
`purchase`. Only `purchase` carries a `value_usd`. A conversion only ever
follows a session that reached `/checkout` or `/signup`.

## Deliberate shapes and edge cases

Aggregates over these databases should not come out uniform, and the awkward
cases a question can trip over are present on purpose:

- 8 of the 59 customers have **no tickets at all**, and 6 have **no sessions**.
- One ticket has **no messages on it** — it was opened and never written to.
- 420 sessions are **anonymous**: `customer_id` and `customer_email` are null.
- 160 sessions have **exactly one page view**, one of them a `/pricing` visit
  that never converted.
- Ticket statuses and priorities are weighted, not uniform: most tickets end up
  resolved, most are medium priority.
- 44 customers have viewed `/pricing` but only 25 ever purchased, so "visited
  the pricing page but never bought" has a real answer.

## Regenerating

Both generated databases come from one committed script with a fixed seed, so
a regeneration reproduces exactly what is committed here:

```bash
python scripts/generate_demo_datasets.py
```

It reads `chinook.sqlite` from this folder for the customer identities and
rewrites `support.sqlite` and `webanalytics.sqlite` in place. Pass `--target`
to write them somewhere else.

`packages/nl2sql/tests/unit/test_demo_datasets.py` regenerates into a
temporary folder and asserts the result matches the committed databases, so
changing the script or the seed without committing the result fails the test
suite. It compares the schema and every row rather than the raw bytes: two
SQLite builds can encode the same rows differently (page layout, and the
header's library version), so a byte comparison against a committed file
passes only on the build that wrote it. Byte-level reproducibility is checked
where it is meaningful — between two runs in one interpreter, which is what
catches an unseeded `random`, a clock read or a dict-ordering dependency.
