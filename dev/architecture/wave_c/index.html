    Wave C: conversation, charts, dashboards, launchpad and MCP over HTTP (design)

    Status: design

    This page is the design for Wave C of the product redesign, which ships as release 0.9. Nothing on it is built yet. Each pull request in the PR plan adds a "Built" note to the sections it builds, as Phase 1 and Phase 2 did. Phase 1 is Configuration v2 and the extension registry; Phase 2 is Phase 2: test bed, storage, providers, policies and adapter SDK v2. Wave A (0.7: events, observers, hooks, approval, evals, routing, drift, sanity checks, MCP over stdio) and Wave B (0.8: glossary and knowledge sources, the review queue, the schema profiler, clarifications, "why this answer", the cost guard, corrections) are designed on their own pages, architecture/wave_a.md and architecture/wave_b.md, which were not merged when this page was written. Wave C uses the names and shapes those pages give, and lists what it needs from them that they do not yet say in Needs from Waves A and B, rather than redesigning them.

    Principles

    The owner set them for the redesign, and they rank above everything below:

    • The package is the product; the playground only demonstrates it. Every capability on this page is a public facade method or an extension point in nl2sql first. The CLI, nl2sql-api, the playground and the MCP server use the public API only. The web UI for conversations, charts and dashboards is Wave D, not here.
    • No active users: design it correctly, not compatibly. No shims, no aliases, no deprecation paths.
    • Never over-engineer. Ship what 0.9 needs; the cut list is part of the design.
    • Configurable in nl2sql.yaml (and its section files) or in code with dependency injection, extensible through the registry, every new action published on the Wave A event bus, and hooks apply to every run this wave adds: a conversation turn, a dashboard tile.

    Three older rules decide most of this wave: the model emits a typed plan, never SQL (dashboards build plans in code, and the model never writes a chart); anything the generator can reject, the validator rejects first (a dashboard filter is a predicate added to a plan before the validator, not text added to SQL); and Wave B's Only an Accept Writes a Person's File, which this wave amends, explicitly and narrowly, for the setup workflow (D123).

    Decisions

    The owner was asleep when this design was written and asked that its recommendations be used, each marked for confirmation. Wave A uses D9 to D35 and Wave B D36 to D59, so Wave C starts at D100. After an independent review, several were amended; those are marked so. Each decision is written into the section it affects.

    # Decision Status Where
    D100 engine.conversations is a namespace over ids, not a live session object. A conversation is stored data; every call names it, so the CLI, nl2sql-api, MCP and a Python caller use it the same way, and a server holds nothing between requests. decided overnight, owner to confirm Conversation
    D101 One rewrite call per follow-up. The first turn, an option chosen from a clarification, a retry and a tool called by name make no rewrite call; every other turn makes exactly one, with the new agent conversation_rewriter and the typed output Rewrite. No heuristic decides that a follow-up "looks standalone". decided overnight, owner to confirm Rewriting
    D102 The rewritten question is what runs, through run_query, unchanged; the pipeline never sees the conversation. Two conversations that rewrite a follow-up to the same question get the same decomposition, so they share the plan cache as any two askers do (its key is the sub-query's intent, the schema version and the knowledge digest). decided overnight, amended after review, owner to confirm Rewriting
    D103 The rewriter sees the last context_turns (3) turns as one JSON block of conversation history, never as instructions: what was typed, the question that ran, its status, the answer's summary, the result's columns and the tables read. No result rows are sent; the summary may quote values from them, as the user already read it. decided overnight, amended after review, owner to confirm Rewriting
    D104 A Wave B clarification is a turn with status needs_clarification. The next turn may name an option (choice=) or be text the rewriter maps to one; a choice re-asks with run_query(pending.question, choice=ClarificationChoice(request=pending, option_id=...)), with no rewrite call. CLARIFICATION_STALE ends that turn error and clears the pending request. decided overnight, amended after review, owner to confirm Clarifications
    D105 A conversation belongs to the (tenant_id, user_id) that started it, and every method requires the caller (user_context, keyword, no default). Roles are never stored: each turn runs with the roles the caller passes now. Another user's conversation is "not found". Callers with no user_id share one "no user" owner, which suits a single-user tool only; nl2sql-api must set a user_id before Wave D exposes conversations. decided overnight, amended after review, owner to confirm Ownership
    D106 Turns are stored without rows, in the state store, for 30 days by default (conversations.max_age_days), purged by engine.storage.purge(). Rows are read from the result store by trace_id while its own retention keeps them. decided overnight, owner to confirm Ownership
    D107 A needs_approval turn is answered by retry, which re-runs the turn's question with the Approvals the asker was given; Wave A's re-run then pins the approved plan. No rewrite call; nothing is stored. decided overnight, amended after review, owner to confirm Clarifications and approvals
    D108 Chat tools are invoked by the user, never chosen by the model. A caller names the tool (conversations.tool(...)), or the user's words ask for it ("chart that") and the rewrite call D101 already makes returns it as a typed ToolCall. The model never calls a tool the user did not ask for, and there is no agent loop. chat_tool stays a registry kind, kept tiny (owner: everything extensible through the registry). decided overnight, amended after review, owner to confirm Chat tools
    D109 The built-in tools make no model call, and a tool reaches the engine through the public facade only, as an app does. The runner that builds tools from the config is the conversation's, not the tools'. decided overnight, amended after review, owner to confirm The interface
    D110 ChartSpec is our own small typed model, with to_vega_lite(). Four kinds: line, bar, big_number, table. Vega-Lite (v5) is the export, not the type. No colour is ever set; the renderer's theme decides. decided overnight, owner to confirm The spec
    D111 The chart is chosen by rules, from the columns' kinds and the plan, with no model call. The one-line takeaway is a template filled from the data; a model-written takeaway is not offered. decided overnight, owner to confirm Choosing a chart
    D112 ResultSummary gains column_kinds (number, text, temporal, boolean, other: Wave A's D30 categories), read from the saved result's schema when it is written. The plan refines them only when the run had one sub-query. decided overnight, amended after review, owner to confirm Choosing a chart
    D113 Diagrams are Mermaid text with no colour and no %%{init} line. The answer view is drawn from the plans; the schema view is an erDiagram from the snapshot's foreign keys, filtered by the caller's scope (caller required) and capped at 30 tables. decided overnight, amended after review, owner to confirm Diagrams
    D114 A report is Markdown assembled from stored turns, with no model call. PDF is out of scope. decided overnight, owner to confirm Reports
    D115 Dashboard tiles come from fixed templates over column roles that the dashboard computes itself: Wave B's role rules (its derived roles and its proposed heuristics) run over the live snapshot, overridden by roles accepted into the glossary; an unaccepted heuristic only picks tiles and never reaches a model. Each template carries its own question text and builds a typed plan in code; generating a dashboard needs an index, not a profile, and makes no model call. decided overnight, amended after review, owner to confirm Choosing the tiles
    D116 A tile is one supplied plan (with its SubQuery) on one datasource, or one verified query, run through run_query(plan=SuppliedPlan(...)), Wave A's pinned-plan path made public (a need from Wave A). A plan that no longer validates marks the tile stale; it is deleted and pinned again. An answer that needed several sub-queries cannot be pinned in 0.9. decided overnight, amended after review, owner to confirm Tiles and refresh
    D117 A dashboard filter is a typed predicate added to a tile's plan before the validator, applied to the tiles whose plan reads the filtered table. Values are checked against the column's type category before the plan is built, because the validator does not type-check literals. decided overnight, amended after review, owner to confirm Filters
    D118 A dashboard is private to its owner in 0.9, and every tile runs as the caller. Tenant sharing, editing a saved dashboard and regenerating a tile wait for Wave D's UI. decided overnight, amended after review, owner to confirm Ownership
    D119 run_query gains answer: bool = True; False skips the answer synthesizer. Tiles use it: a tile shows a chart, not a paragraph. decided overnight, owner to confirm Tiles and refresh
    D120 scan() looks in three places, each declared by the adapters: a connection URL the caller passes (nl2sql launch passes DATABASE_URL), database files under the folder by the suffixes adapters declare (two levels deep), and the default ports adapters declare, on 127.0.0.1 only. Nothing in the engine names a database. decided overnight, owner to confirm Finding a database
    D121 The Connect routes in 0.9 are datasource-types, datasource/test and the existing POST /datasource. No scan route (the server's files and ports are not the user's) and no profile or review routes (Wave B defers them to Wave D, and a profile of a large schema is a job, not a request). decided overnight, amended after review, owner to confirm Connect a database over REST
    D122 No secret value is ever written into YAML. The config writer writes every secret field (a connection's secret fields, an LLM or embeddings api_key, a secret provider's credentials) as ${env:NL2SQL_...} and the value into the .env beside nl2sql.yaml, or refuses. .env is written by nl2sql launch, and by the REST route only on the fresh local install nl2sql-api already treats as admin (no role source, loopback client). decided overnight, amended after review, owner to confirm Writing the config
    D123 Three writers join accept in Only an Accept Writes a Person's File: write_project (new files only, refuses to overwrite), engine.datasources.save (one datasource file, refused when it changed since the engine loaded it) and write_env_values (the .env). This overrides Phase 1's and Phase 2's "persisting a change is the calling app's job": the web form, the terminal and launch need the same writer, and the package is the product. decided overnight, amended after review, owner to confirm Writing the config
    D124 Starter questions are the dashboard templates' questions (five), printed and filed as review-queue proposals (kind example, a need from Wave B); they reach glossary.yaml's examples, and so routing, only through a person's accept. decided overnight, amended after review, owner to confirm nl2sql launch
    D125 nl2sql launch does not verify the model key with a call. The first question the user asks is the check. decided overnight, owner to confirm nl2sql launch
    D126 MCP over HTTP is nl2sql mcp --http, the MCP SDK's streamable HTTP transport in stateless mode, in its own process, with the caller's identity resolved per request. It is not mounted in nl2sql-api in 0.9. decided overnight, amended after review, owner to confirm MCP over HTTP
    D127 Authentication is API keys first (bearer); OAuth later. Keys are made by engine.api_keys (an admin caller required), stored hashed in the state store, and each carries the user_id, tenant_id and roles its holder runs as. Binding to anything but loopback without keys is refused. decided overnight, amended after review, owner to confirm Authentication
    D128 The hosted demo does not expose MCP in 0.9. It serves recorded answers with no key, so an MCP client could ask nothing new; exposing it waits for OAuth and a decision on whose key pays. decided overnight, owner to confirm MCP over HTTP
    D129 The first PR adds every Wave C shape at once, and the stubs the tracks share: the four facade namespaces, the chat-tool entry points, the keys and launch commands, the docs pages in the nav and the boundary test's constants, so the parallel PRs touch different files. decided overnight, amended after review, owner to confirm PR plan
    D130 Every Wave C method that reads or writes something owned, scoped or privileged requires the caller (user_context, or by for a writer), keyword-only with no default, and fails closed: the conversations, dashboards and API-key methods, datasources.diagram, datasources.save and dashboards.suggest_questions. The CLI builds an explicit context (--as ROLE), as Wave B's nl2sql review does. decided after review, owner to confirm Every section

    1. Goals and non-goals

    What ships in 0.9

    Goal What it means
    Conversation engine.conversations: start, ask, stream, retry, tool, report, get, list, delete. A follow-up is rewritten into a self-contained question by one typed model call and run unchanged. Every turn keeps what was typed, what ran, its result and its trace_id. Clarifications and approvals are turns. Stored per user with retention.
    Chat tools A small chat_tool registry kind and four built-ins: chart, diagram, report, pin. Asked for by name or in the user's words; never picked by the model on its own.

    Launchpad nl2sql launch (and uvx --from nl2sql-engine nl2sql launch): find a database, test it, write the config, set the model key, index, profile and review, five starter questions. Every step is a package method.
    Connect a database over REST Thin nl2sql-api routes over types() and test(), and a POST /datasource that answers a bad body with a 422 and can save.
    MCP over HTTP nl2sql mcp --http with API-key auth, per-request identity, and follow-ups and clarifications in ask.

    3. Conversation

    The shape

    # nl2sql/conversations/models.py (engine: a turn holds a QueryResult)
TurnKind = Literal["question", "choice", "tool", "retry"]
TurnStatus = Literal["answered", "needs_clarification", "needs_approval", "stopped", "error", "tool"]

class Turn(BaseModel):
    index: int                         # 1-based, in the order asked
    at: datetime                       # UTC
    kind: TurnKind
    text: str                          # what the user typed, or the chosen option's label
    question: str | None               # what ran; None for a tool turn
    rewritten: bool                    # question differs from text
    refers_to: list[int] = []          # the turns the rewrite drew on
    status: TurnStatus
    trace_id: str | None               # the run's id: its events, trace and result pages
    result: QueryResult | None         # stored without rows (D106)
    tool: ToolOutput | None = None     # a tool turn's output (section 4)
    error: dict[str, Any] | None = None   # code and message, for a tool turn or a turn with no result

class Conversation(BaseModel):
    id: str                            # random, 22 url-safe characters
    tenant_id: str | None
    user_id: str | None                # the owner (D105)
    title: str                         # the first question, cut at 80 characters
    datasource_id: str | None          # when set, every turn skips routing
    created_at: datetime
    updated_at: datetime
    turns: list[Turn]
    pending: ClarificationRequest | None   # Wave B's request the last turn ended with

class ConversationInfo(BaseModel):
    id: str; title: str; updated_at: datetime; turns: int

    Conversation, Turn and ConversationInfo are exported from nl2sql. A turn's result.sub_queries[].rows is always None once stored; everything else of the QueryResult is kept, so a turn shows its SQL, plan, explanation, validation, warnings, source and usage without its trace.

    The facade

    Every method takes user_context keyword-only and required (D105, D130).

    Method What it does
    engine.conversations.start(*, user_context, datasource_id=None) -> Conversation A new, empty conversation owned by the caller. Nothing runs.
    engine.conversations.ask(conversation_id, text=None, *, user_context, choice=None, execute=True, cancellation_token=None) -> Turn One turn: rewrite (when D101 says so), run, store. choice is an option id of the pending clarification, given instead of text.
    engine.conversations.stream(conversation_id, text=None, *, user_context, choice=None, execute=True) -> Iterator[Event] As ask, yielding Wave A's caller-safe run events, with conversation.rewritten after run.started and conversation.turn (the stored Turn as JSON) as the terminal event. Closing the iterator early cancels the run; no turn is stored.
    engine.conversations.retry(conversation_id, *, user_context, approvals=[]) -> Turn Re-runs the last question turn's question as a new turn of kind retry (D107), with no rewrite call. For an approval, a timeout or a stopped run.
    engine.conversations.tool(conversation_id, name, args=None, *, user_context) -> Turn Calls a chat tool by name as a turn of kind tool (section 4).
    engine.conversations.report(conversation_id, *, user_context, turns=None, title=None) -> str The Markdown report (Reports); the report tool calls it.
    engine.conversations.get(conversation_id, *, user_context) -> Conversation One conversation, with its turns
    engine.conversations.list(*, user_context, limit=20) -> list[ConversationInfo] The caller's conversations, newest first
    engine.conversations.delete(conversation_id, *, user_context) -> None Deletes it and its turns; its results stay until their own retention

    Every method raises ConversationNotFound (a LookupError) for an id that does not exist or is not the caller's. ask, stream, retry and tool on a conversation that is already running a turn raise ConversationBusy: the turn holds the state store's lock conversation:<id> (Phase 2's StateStore.lock) for the pipeline's timeout_s plus ten seconds.

    # nl2sql/conversations/models.py
class ToolCall(BaseModel):
    name: str                          # an enabled chat tool
    args: dict[str, Any] = {}          # validated by that tool's args_model

    4. On REWRITE_FAILED, the conversation API builds a QueryResult with status error and the code without a graph run, and closes the scope with run.finished, so every turn's scope closes exactly once.

    Clarifications and approvals in a conversation

    • A clarification (D104). A run that ends needs_clarification stores a turn with that status and sets Conversation.pending to the result's clarification (ClarificationRequest). The next turn may pass choice="b", or text the rewriter maps to an option ("the second one", "by order date"). Either way the engine calls run_query(pending.question, choice=ClarificationChoice(request=pending, option_id=...)): Wave B refuses a choice unless the question equals the request's, so the request's own question is passed, not the typed text. The turn's kind is choice and its text is the option's label. CLARIFICATION_STALE (the schema or the glossary changed) ends the turn error with Wave B's message. Any next turn clears pending; a choice with nothing pending raises ValueError ("Nothing in this conversation is waiting for a choice.").
    • An approval (D107). A run that ends needs_approval stores a turn with that status and the result's approvals_needed. An approver acts on each ApprovalRequest outside the conversation (an app shows it, as Wave A describes); the asker then calls retry(conversation_id, user_context=, approvals=[...]), which re-runs the last question turn's question with those approvals. Wave A checks that the request's question and asker are this run's and pins the approved decomposition and plan; different SQL asks again, as everywhere.

    4. Chat tools

    Invoked, not chosen (D108)

    A chat tool turns something the conversation already has into something else: a chart, a diagram, a report, a dashboard tile. It never asks the database a new question. A tool runs only when the user asks for it:

    1. By name. engine.conversations.tool(cid, "chart", {"turn": 3}, user_context=...). A UI button, an MCP client or a script does this.
    2. In words. "Chart that", "draw the tables behind this", "write this up", "pin it to my sales dashboard". The rewrite call D101 already makes returns kind: "tool" with a typed ToolCall, so asking in words costs nothing extra.

    The model never calls a tool on its own initiative, and nothing loops: one turn is one question run or one tool call.

    to_vega_lite() returns a Vega-Lite v5 spec with the rows inline (data.values), mark line, bar or (for a big number) a text mark, temporal or nominal x, quantitative y, several measures folded with a fold transform, and a color encoding only for series.     Choosing a chart

    engine.results.chart(result, result_id=None, *, kind=None, tenant_id=None) -> ChartSpec. result is a QueryResult (its plan is used) or a trace_id (only the columns' kinds are). kind forces a kind the data can draw, else ValueError naming the ones it can. It reads results as engine.results.page does, by trace_id and tenant (B13 unchanged).

    Column kinds (D112). The artifact writer records each column's kind when it writes the parquet file, from the Arrow type, into ResultSummary.column_kinds: integer, decimal and float are number; date, time and timestamp are temporal; string is text; bool is boolean; anything else other. When the run had one sub-query, its plan refines the kinds of the result's columns, matched by the select items' aliases:

    • a select item that is DATE_TRUNC(unit, x) is temporal (the plan's portable DATE_TRUNC returns an ISO string);
    • a select item that is DATE_PART('year', x) and is grouped on is temporal (a year axis);
    • a select item that is an aggregate (SUM, COUNT, AVG, MIN, MAX) is a measure; a grouped column is a dimension.

    With several sub-queries (an aggregated result) or no plan (a verified query, a trace_id), every number is a measure and everything else a dimension.

    The rules (D111), first match wins:

    # Shape of the result Chart
    1 One row, one measure (and at most one text column, a label) big_number
    2 One temporal dimension, one to max_series (5) measures, at least two rows line, x sorted ascending
    3 One temporal and one text dimension with at most max_series distinct values, one measure line with series
    4 One text or boolean dimension, one to three measures, two to max_categories (20) rows bar, in the result's order when the plan ordered it, else by the first measure descending
    5 Anything else, or more than max_points (1,000) rows for a line table

    The data is read up to max_points rows; when the result has more, data.truncated is true and a line chart becomes a table rather than drop points silently.

    The takeaway. One sentence from a template, filled from the data, with no model call:

    Chart Template
    line "{y} went from {first} in {x0} to {last} in {xn} ({change:+.0%})." For a series, the series with the largest last value.
    bar "{top} has the highest {y}: {value}." When every value is non-negative and the measure is a SUM or COUNT: "...{value}, {share:.0%} of the total shown."
    big_number "{y}: {value}."
    table none

    Numbers are written with thousands separators and at most three significant digits after the point; a null first or last value gives no change.

    Filters

    A filter value becomes a predicate added to a tile's plan before the validator (D117), never text added to a question or SQL:

    1. Values are checked first. The validator does not compare a literal with its column's type, so refresh does, against the filter's kind: a number takes ints and floats, temporal an ISO date or timestamp string, boolean a bool, text a string; in takes 1 to 100 values, between exactly two. A failure is a ValueError naming the filter, and nothing runs.
    2. Where it applies. For each active filter, find the tile plan's TableRef for the filter's schema.table. A plan that does not read that table runs unfiltered, and its TileRun.filtered is False, so the UI can say so.
    3. The predicate. between [a, b] is col >= a AND col <= b; in [v1, v2] is (col = v1 OR col = v2 ...). Both use only the binary operators the plan and generator already have, with the values as plan literals. The predicate is joined to the plan's where with AND.
    4. Then the usual path. plan.after, the validator (columns, scope) and the generator, which renders the literals as it renders any literal.

    filters maps filter ids to values; an id the dashboard does not have is a ValueError.

    Ownership

    • Private (D118). A dashboard is seen and changed by its owner only (tenant_id and user_id, as a conversation); another caller gets DashboardNotFound.
    • Runs as the caller. generate, refresh and filter_values run with the caller's user_context. A tile reading a table the caller's scope no longer reaches is denied, exactly as the question would be. Nothing in a saved dashboard carries a grant.

    Finding a database: scan()

    # nl2sql_sdk/discovery.py (pydantic and the standard library only)
class Found(BaseModel):
    kind: Literal["url", "file", "port"]
    value: str                           # the URL, the file path, or "127.0.0.1:5432"

@runtime_checkable
class DiscoverableAdapter(Protocol):     # optional: an adapter without it is never found, only chosen
    file_suffixes: ClassVar[tuple[str, ...]]      # (".sqlite", ".sqlite3", ".db")
    default_ports: ClassVar[tuple[int, ...]]      # (5432,)
    url_schemes: ClassVar[tuple[str, ...]]        # ("postgresql", "postgres")
    @classmethod
    def connection_for(cls, found: Found) -> dict[str, Any] | None:
        """The connection fields this finding fills in, or None when it is not this adapter's
        (a .db file that is not SQLite). Never connects."""

    # engine.datasources
def scan(self, folder: str | Path = ".", *, url: str | None = None,
         ports: bool = True) -> list[Candidate]: ...

class Candidate(BaseModel):
    type: str                            # the adapter's registry name
    title: str
    found: Found
    connection: dict[str, Any]           # what was filled in; repr masks secret fields
    missing: list[str]                   # required fields the form still needs
    installed: bool
    install_hint: str
    Rule Detail
    Declared by adapters (D120) The suffixes, ports and URL schemes are class variables on each adapter, and connection_for is the adapter's. The engine loops over the registry's adapters (installed or not, as types() does) and names no database itself, so the dialect rule holds and a plugin adapter is found the same way.
    A URL url's scheme, up to any +driver, is matched against url_schemes. The caller passes it; nl2sql launch passes DATABASE_URL, the only new environment read (an entry point's, on the allow-list).
    Files Under folder, two levels deep, skipping hidden folders and storage.path, at most 50 files, matched by suffix, then confirmed by connection_for (which may read a file's first bytes, as SQLite's SQLite format 3 header).
    Ports With ports, a TCP connect to 127.0.0.1 on each declared port with a 0.2 s timeout. Loopback only. An open port fills host and port; the rest is missing.
    Order URL, then files, then ports; duplicates once.
    Never connects scan opens no database session; test() does.

    The five built-in adapters declare: SQLite (.sqlite, .sqlite3, .db, URL sqlite), DuckDB (.duckdb, URL duckdb), PostgreSQL (5432, postgresql, postgres), MySQL (3306, mysql, mariadb) and SQL Server (1433, mssql, sqlserver).

    Function What it writes

    Its value Written as
    A reference (${env:VAR}, ${vault:path}) The reference, unchanged
    A literal, where the writer may write .env (write_project from launch; save(env_file=True)) ${env:NAME} in the YAML and NAME=value in .env
    A literal, otherwise Refused: SecretValueInConfig naming the field, with the fix "pass ${env:VAR} or a secret provider reference"

    The transport (D126)

    nl2sql mcp --http [--host 127.0.0.1] [--port 8765] serves Wave A's MCP server over the MCP SDK's streamable HTTP transport at /mcp, in stateless mode with JSON responses: each request stands alone, which is all the tools need, because a follow-up names its conversation_id. stdio stays the default. The server is its own process, built on the same nl2sql/mcp/server.py; mounting it in nl2sql-api is Wave D.

    Rule Detail
    Identity per request One engine serves every request. An auth middleware verifies the bearer token and sets a context variable to the key's UserContext for that request; the tools read it through the identity callable build_server(engine, identity) takes (need A6). stdio passes the --role/--user context as a constant.     Host and Origin The SDK's TransportSecuritySettings with DNS-rebinding protection on, allowed_hosts and allowed_origins from the config, rather than a check of our own.
    Binding A host that is not loopback with auth: none refuses to start, naming the fix. TLS is a reverse proxy's or a tunnel's job; the docs show both, and say remote chat apps require https.
    Logs As stdio: to stderr, with the trace_id of each ask
    Extra The mcp extra (Wave A), plus uvicorn for the HTTP server. Only nl2sql/mcp/, nl2sql/cli/demo/ and nl2sql/cli/commands/demo.py import Starlette or Uvicorn.

    Authentication: API keys (D127)

    # engine.api_keys (caller required on every method that manages keys, D130)
def create(self, *, user_id: str, roles: list[str], by: UserContext,
           tenant_id: str | None = None, label: str = "") -> tuple[ApiKey, str]: ...
def list(self, *, by: UserContext) -> list[ApiKey]: ...
def revoke(self, key_id: str, *, by: UserContext) -> None: ...
def verify(self, token: str) -> UserContext | None: ...

class ApiKey(BaseModel):              # never the secret
    id: str                           # 8 characters, shown in lists and logs
    label: str
    user_id: str
    tenant_id: str | None
    roles: list[str]
    created_at: datetime
    created_by: str | None
    revoked_at: datetime | None
    Rule Detail
    The token nl2sql_<id>_<secret>, the secret 32 random bytes, URL-safe. create returns it once; only sha256(secret) is stored, in the state store. A high-entropy secret needs no salt or slow hash.
    Verify Looks the key up by id, compares the hash with hmac.compare_digest, and returns the key's UserContext (its user_id, tenant_id, roles) or None for a malformed, unknown or revoked key.
    Who may manage keys by must hold a policies.admin_roles role, else PermissionError. There is no default: a caller that forgot it fails closed. roles must name configured roles.
    Identity to role Each key carries the roles its holder runs as. Nothing is inferred from the client; a key per person or per app is the unit of revocation.
    On the wire Authorization: Bearer <token>. Missing or invalid: 401 with WWW-Authenticate: Bearer, and mcp.denied (reason: missing, malformed, unknown, revoked; the key id when there is one; never the token), which the audit observer keeps.
    CLI nl2sql keys create --as ROLE --user NAME --role analyst [--tenant T] [--label L] prints the token once; nl2sql keys list --as ROLE; nl2sql keys revoke ID --as ROLE. --as builds the admin by, as Wave B's nl2sql review --as ROLE does.
    OAuth later A client that lets its user set a header (a desktop assistant's config file, an IDE, a script using a model provider's remote MCP tool with headers) works with keys. A chat app's connector screen that offers only OAuth does not, which is why OAuth is the next step after 0.9.

    engine.api_keys is the engine's and not MCP's, so Wave D's nl2sql-api can accept the same keys.
