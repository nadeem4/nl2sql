    Wave A: events, observers, hooks, evals and routing (design)

    Status: design

    This page is the design for Wave A of the product redesign, which ships as release 0.7. Each pull request in the PR plan adds a "Built" note to the sections it builds, as Phase 1 and Phase 2 did; A0 (the foundation), E1, H1, H2, V1, E2, V2, E4, S1 and D1 are built. Phase 1 is Configuration v2 and the extension registry; Phase 2 is Phase 2: test bed, storage, providers, policies and adapter SDK v2. Wave A is what those pages called "Phase 3", plus the cross-database routing work ("Phase R") and three smaller tracks.

    Principles

    The owner restated them for Wave A, and they rank above everything below:

    • The package is the product; the playground only demonstrates it. Every capability is a public facade method or an extension point first. The CLI, nl2sql-api, the playground and the MCP server use the public API only, and nothing in this design exists only in one of them.
    • No active users: design it correctly, not compatibly. No shims, no aliases, no deprecation paths. Where a 0.6 shape is wrong, 0.7 replaces it.
    • Never over-engineer. Ship what 0.7 needs; the cut lists below are part of the design.
    • Everything is configurable in nl2sql.yaml (and its section files) or in code with dependency injection, extensible through the registry, and events and observability apply everywhere: a question on the generated or the verified-query path, an index build, a purge, an LLM swap, from the CLI or the server. Hooks apply to every run, on both paths; there is no hook on an index build in 0.7.

    Two older rules shape this wave in particular: the model emits a typed plan, never SQL (it decides how evals are seeded), and anything the generator can reject, the validator rejects first (it decides where the join-key check and the hook boundary live).

    Decisions

    The owner was asleep when this design was written and asked that its recommendations be used, each marked for confirmation. D9 to D13 were already on record from the final redesign; D14 onwards are new. Each decision is written into the section it affects. An independent review of the first draft (PR #308) changed several of them; those are marked amended after review and are still the owner's to confirm.

    D12 Evals use curated answers by default and record each answer's source; every case a verified query answered is also run with curated answers off, so the report has a generated-only accuracy over every case.     D13 No masking at execute.after on day one. After the validator a hook may only allow, deny or ask for approval. decided overnight, owner to confirm Hooks

    D16 policy.decision is published for denials, at the enforcement points only: the validator's table refusal, the curated matcher's refusal of a verified query, and the resolver's datasource refusal.     D18 OpenTelemetry becomes the otel extra and an observer. settings.observability is replaced by an observers: section; with no section the engine runs log and audit. decided overnight, owner to confirm Observers
    D19 The audit log moves under storage.path (audit/, JSON lines, 90 days, purged by engine.storage.purge()), written by the audit observer: one summary line per run (who, which datasources and tables, status, source) plus the denials, approvals, limits and changes. common/event_logger.py is deleted (bug B27). decided overnight, amended after review, owner to confirm Built-in observers
    D20 Caps: max_llm_calls defaults to 60, max_cost_usd to none. A cost cap with a configured model the price table cannot price is a ConfigError when the engine is built. decided overnight, owner to confirm Per-question caps
    D21 The six hook points are run.before, datasources.after, plan.after, execute.before, execute.after and answer.after. The first three may modify; the last three may not. decided overnight, owner to confirm The six points
    D22 No built-in hooks in 0.7. The docs carry a 30-line example; the tests use fakes. decided overnight, owner to confirm Hooks
    D23 Hooks run in config order. The first deny ends the point; modifications chain, each hook seeing the previous one's output. decided overnight, owner to confirm Hook decisions
    D24 An approval is bound to the asker and checked by the engine. The request's id hashes the question, the asker's user_id and tenant_id, the hook, the datasource, the plan and the SQL's hash; the engine recomputes it, and an approval for another asker or another request is refused. Approvers are the hook's approver_roles, by default policies.admin_roles. An approved decision counts as Allow, and the next hook at the point still runs. An Approval is not signed and does not expire: it is trusted exactly as far as the UserContext a caller passes is trusted today. decided overnight, amended after review, owner to confirm Approval
    D25 engine.evals only. No top-level engine.evaluate (the top level stays questions only). engine.benchmark, BenchmarkAPI, BenchmarkConfig and nl2sql benchmark are deleted. decided overnight, owner to confirm The facade
    D26 Seeding asks the model for questions and typed plans, never SQL, five per call, under a cost cap (max_cost_usd, by default evals.yaml's). The engine's validator and generator turn each plan into SQL, the adapter runs it read-only, and the case is written with status: draft. decided overnight, amended after review, owner to confirm Seeding
    D27 regenerate runs gold SQL through the datasource's adapter. evaluation/gold.py's direct sqlite3 use and its boundary exemption go. decided overnight, owner to confirm Regenerating expected rows
    D28 Routing fuses five signals with reciprocal rank fusion (k = 60), keeps the top 3 (candidates defaults to 3), and drops a datasource whose best entry similarity is under half the most similar datasource's: the floor is on similarity, not on the fused score, because the fused scores of a handful of datasources are always within a few percent of each other. A datasource a signal did not rank gets the rank after the last one it did, so having entries of a type (only one datasource with verified queries, say) is not a vote. Only entries the caller's scope allows vote: a hidden table or column, or a verified query that reads a hidden table, never votes or reaches the trace. candidates, max_datasources, max_sub_queries and floor_ratio are settings; the vote depth and the fusion constant stay constants until a measurement asks for a knob. decided overnight, amended after review (twice: the floor on similarity, the absent rank, table scope, after the review of PR #316), owner to confirm Phase R
    D29 A decomposition over max_sub_queries ends the run with QUESTION_TOO_BROAD, whose message asks for a narrower question. It is not retried. decided overnight, owner to confirm Limits
    D30 Join keys are coerced, not just checked. The engine's aggregator casts both sides of a join key to the declared dtype (in polars, so no dialect is involved), and a value that does not convert is a warning. The validator rejects only categories that cannot be coerced (temporal against number or boolean); an unknown type is not checked. The plan has no CAST, so the validator never asks the model for one. decided overnight, amended after review, owner to confirm The join-key type check
    D31 Structural diffs are stored with the new version in the state store (store interface version 2). A rename is reported as a drop and an add. index.check() never re-indexes. decided overnight, owner to confirm Schema drift
    D32 Sanity checks: a missing filter value with a close match, and a confirmed fan-out under COUNT (repairable as COUNT(DISTINCT ...)), are retried once. A fan-out under SUM or AVG (the plan has no derived tables to repair it), an all-null column, a missing value with no close match, and any check with no retry left are warnings. Many-to-many sums are one case of JOIN_FAN_OUT, not a code of their own. decided overnight, amended after review, owner to confirm Answer sanity checks
    D33 MCP is stdio only in 0.7, behind the mcp extra; the caller's role comes from nl2sql mcp --role, by default policies.default_role, and with neither the server refuses to start, except under policies.allow_all, where it starts and logs a warning that every table is readable; an unknown --role is refused, allow_all included. Over MCP a refusal is always the generic one, whatever refusal_names_tables says. engine.datasources.schema() requires a user_context and hides denied tables (bug B29); there is no default admin view, and the playground's /api/schema requires its role. decided overnight, amended after review (twice: the second after the attack review of PR #325), owner to confirm MCP server
    D34 QueryResult.warnings is typed (RunWarning: code, node, message, sub_query_id, detail), replacing the list of dicts. It lands with the sanity checks (S1), the PR that adds warnings, not in the foundation. decided overnight, amended after review, owner to confirm Answer sanity checks
    D35 The first PR adds the shared shapes, and only those: the SDK's Event and Observer, the bus, the catalog, RunScope with its publish slots, the registry kinds, the config shapes, the error codes, the new status, stop and approvals_needed result fields, and stub engine.events and engine.evals namespaces. The parallel PRs then never edit config/models.py, common/errors.py, events/run.py or public_api.py's namespace list; the overlaps that remain are listed in the PR plan. decided overnight, amended after review, owner to confirm PR plan

    1. Goals and non-goals

    What ships in 0.7

    Goal What it means
    An event bus Synchronous and in process. Typed events for a run and its steps, model calls, hook and policy decisions, index builds, drift, purges, LLM swaps and evals. engine.events.subscribe(); stream_query yields the run's events, each ready to send as a Server-Sent Event.
    Observers A registry kind (nl2sql.observers). Built-in log (correlated: every line carries its trace_id), audit and otel (the otel extra). import nl2sql loads no opentelemetry. Observers fail open.
    Cost and caps A dated price table in llm/. A cap on each question's cost and on its model calls, ending the run as stopped with a typed reason.
    Hooks Six points through a run, a registry kind (nl2sql.hooks), fail closed with a per-hook on_error: open. Modify before the validator, deny only after it, held by an architecture test.
    Approval A run that ends needs_approval, and a re-run that carries the approval.
    Evals as a product engine.evals, evals.yaml and suite files, five scorers behind a Scorer interface (nl2sql.scorers), regenerate through the adapter, the regression gate, nl2sql eval, and seeding a draft gold set from your own database. The Chinook gold set moves over unchanged.
    Phase R Routing on one entry per example phrasing, table and column votes and reciprocal rank fusion; up to 3 datasources and 6 sub-queries per question; retrieval limits as settings; join keys coerced in the aggregator and checked in the validator; routing evals beyond Chinook as the gate.
    Schema drift, measured engine.index.check() and nl2sql index --check, a stored structural diff per version, its impact on verified queries and policies, and a schema.drifted event.
    Answer sanity checks Join fan-out, many-to-many sums, all-null columns and missing filter values, as typed warnings or one retry.
    An MCP server nl2sql mcp over stdio with ask, list_datasources and describe_table, on the public facade only.

    3. The event bus

    The event

    # nl2sql_sdk.events (pydantic and the standard library only, D14)
class Event(BaseModel):
    model_config = ConfigDict(frozen=True)
    name: str                    # "node.finished", from the catalog
    at: datetime                 # UTC
    trace_id: str | None = None  # the run's id; None for an engine event (an index build)
    tenant_id: str | None = None
    data: dict[str, Any] = {}    # JSON-ready; the catalog's model for this name, dumped

    def sse(self) -> str:        # "event: <name>\ndata: <json>\n\n"
        ...

class Observer(Protocol):
    interface_version: ClassVar[int]           # 1
    config_model: ClassVar[type[BaseModel]]
    events: ClassVar[frozenset[str] | None]    # the names it wants; None means every event
    @classmethod
    def from_config(cls, cfg: BaseModel, *, folder: Path) -> "Observer": ...   # folder: storage.path
    def on_event(self, event: Event) -> None: ...
    def close(self) -> None: ...

    trace_id is the name the facade already uses for a run (QueryResult.trace_id, engine.traces.get, engine.results), so an event, a log line, a trace and a result page all join on one value.

    The bus

    # nl2sql/events/bus.py
class EventBus:
    def subscribe(self, fn: Callable[[Event], None], names: Iterable[str] | None = None,
                  *, fail: Literal["open", "raise"] = "open") -> Subscription: ...
    def publish(self, name: str, data: BaseModel | Mapping[str, Any] = {}, *,
                trace_id: str | None = None) -> Event: ...
    def close(self) -> None: ...               # closes every observer it built
    Rule Detail
    Synchronous, in process publish calls each subscriber in subscription order, on the publishing thread, and returns. There is no queue and no worker. A slow observer slows the run; the docs say so, and otel exports in its SDK's own background thread.
    One bus per engine Runtime.bus, built with the runtime. Two engines in one process share nothing (the invariant An Engine Owns Its Config).
    Observers fail open (D9) An exception from a subscriber is caught, logged once per subscriber and event name at WARNING, and counted (EventBus.failures). The bus never raises into the engine. The internal run collectors subscribe with fail="raise", because a broken collector is an engine bug a test must see.
    Thread safety Sub-queries run on LangGraph's worker threads, so publish is called concurrently. The bus holds its subscriber list immutably (copy on subscribe); an observer that keeps state locks it.
    Checked names publish refuses a name the catalog does not list (a ValueError: an engine bug), and validates data against the name's model. A test scans every publish("...") call site for catalogued names.

    Engine events go through ctx.bus. Code that runs outside a question (an index build, storage.purge, replace_llm, index.check, a datasource check, an eval run) publishes with ctx.bus.publish(...) explicitly; it always holds the runtime.

    Run events go through the run's scope. A RunScope (nl2sql/events/run.py) is the life of one question on the bus. Where it sits follows from the code as it is:

    1. It is opened by the caller that builds the result: QueryAPI.run_query and stream_query, and the eval runner. run_with_graph returns graph state; the QueryResult is built afterwards by result_from_state in QueryAPI (api/query_api.py), so only there can run.finished be published with the result's summary. The scope makes the run's trace_id and hands it to run_with_graph, which puts it in GraphState.
    2. Its context is entered inside the worker. run_with_graph submits the graph to its own ThreadPoolExecutor with the caller's copy_context() (pipeline/runtime.py; 0.6 submitted it without one), so the worker inherits the caller's context variables (a request's keys, the run's pinned LLM set), and policy_engine.run() is entered inside _invoke. The scope's context variables (the trace_id, the tenant_id and the scope itself) are entered there too, beside it; LangGraph's own worker threads then inherit them, as they already inherit current_datasource_id. Code deep in a run (the structured-output retry in llm/wires/, the hook runner, the budget, the enforcement points) publishes with the module function nl2sql.events.publish(name, data), which reads the scope from the context and is for code inside a RunScope only: outside one it does nothing. The same context variable is what TraceContextFilter reads, which fixes the null trace_id on every log line (B14).
    3. It closes exactly once. run.finished (with the summary) when QueryAPI has the result, or run.failed when run_with_graph raised or the result could not be built. Both are published on the bus, so the audit observer and the otel run span see a crashed run too.
    4. A closed scope drops what comes after. A timed-out run is answered while its graph winds down in the background (run_with_graph's TimeoutError branch); the llm.call and node.* events it publishes after run.finished are dropped and counted (RunScope.late_events), so no observer sees a run continue after it ended. The usage in run.finished is what was spent until the answer; the docs say a timed-out run may spend a little more.

    engine.stream_query yields Events (D17). QueryEvent, its type literal and the names node_started, node_finished, result_manifest, answer_delta, final and error are deleted. event.sse() is the event as one Server-Sent Event, which is all nl2sql-api's POST /query/stream sends.

    6. Hooks

    A hook is code the operator registers that sees a run at fixed points and may let it continue, change what it carries, stop it, or ask for approval. No hook ships built in (D22).

    • Modify before the validator, deny only after (D21, D13). A plan a hook changed at plan.after is validated like any other, so a hook can never smuggle in what the validator forbids, including a table the role may not read. After the validator nothing may change the SQL, the plan or the result; a hook may only stop it. datasources.after may only remove datasources: the resolver re-applies the scope check to what the hook returns, and an added id is a hook error.
    • The verified path has no routing and no plan, so only run.before, execute.before, execute.after and answer.after apply. A deny there ends the run; it does not fall back to the generated path, because a deny means no.
    • A plan-only run (execute=False) never reaches the execute.* points.
    • Deny scope. A deny at a per-sub-query point (plan.after, execute.before, execute.after) may name scope="sub_query", which drops that sub-query (the answer says so) and lets the others continue; the default is scope="run". This is the only narrowing after the validator. A sub-query that feeds a join or compare combine group cannot be dropped alone, since the group would have one side: the whole group is dropped, with its post-combine operations, and the answer says which part of the question went unanswered and why.
    • The plan cache keeps the planner's plan. graph_utils caches the planner's response after a clean execution. It stores the plan the planner (or the cache) produced, before any plan.after hook changed it, and plan.after runs on every cache hit. So a hook's change is never cached, is applied fresh on each run, and stops applying the moment the hook config changes. test_cached_plan_is_the_planners_not_the_hooks holds it.

    Decisions and the runner

    nl2sql/hooks/runner.py holds HookRunner.call(point, ctx) -> Decision, built once per engine from the config, and the table of points (HOOK_POINTS: each point's allowed decisions and the fields Modify may set there).

    Rule Detail
    Order (D23) Hooks run in config order. A Modify replaces the fields it sets, and the next hook sees the result. The first Deny, or NeedsApproval without a matching approval, ends the point; later hooks are not asked. A NeedsApproval the run's approvals cover counts as Allow, and the next hook still runs (D24).
    Fails closed (D9) An exception, a return value that is not a Decision, or a decision the point does not allow (a Modify at execute.before, a NeedsApproval at plan.after) is a hook error, which denies with HOOK_FAILED and the hook's name. With on_error: open on that hook, an exception is logged and treated as Allow; a disallowed decision still denies, because it is a bug in the hook, not an outage.
    Timeouts The hook owns them, as a PolicyCheck does; the pipeline's timeout_s bounds the run anyway.
    Events Every call publishes hook.decision; the audit observer keeps the denials, approvals and errors.
    Errors Deny becomes a PipelineError HOOK_DENIED (CRITICAL, not retryable) whose message is the hook's reason, and whose details name the hook and the point. A run-scoped deny ends the run with status: "error".

    7. Approval

    A hook at execute.before answers NeedsApproval("Reads payroll.salaries"). The minimal shape (D10, D24):

    class ApprovalRequest(BaseModel):          # on QueryResult.approvals_needed
    id: str                                # sha256 over every field below except reason and approver_roles, hex
    question: str
    asker_user_id: str | None              # the run's UserContext
    asker_tenant_id: str | None
    hook: str
    point: Literal["execute.before"]
    datasource_id: str
    decomposition: DecomposerResponse | None   # generated path: the run's decomposition
    sub_query: SubQuery | None                 # generated path: the sub-query the SQL answers
    plan: PlanModel | None                     # generated path: its validated plan
    verified: VerifiedRef | None               # verified path: the query id and its bound params
    sql: str
    sql_sha256: str
    reason: str
    approver_roles: list[str]              # for display; the engine checks the hook's configured roles

class Approval(BaseModel):                 # passed back on the re-run
    request: ApprovalRequest
    by: UserContext                        # the approver
    1. The run ends. The sub-query does not run, the others finish the step they are on, nothing is aggregated or synthesized, and the result has status: "needs_approval", approvals_needed (one ApprovalRequest per pending sub-query), an error NEEDS_APPROVAL and the answer "This question needs approval before it runs: Reads payroll.salaries." hook.decision is published and audited.
    2. The approver re-runs it. An app shows the request to someone with an approver role, who calls engine.run_query(question, user_context=<the asker>, approvals=[Approval(request=..., by=<the approver>)]). run_query and stream_query gain the approvals argument.
    3. The re-run pins what was approved. The plan cache cannot do it: it holds only plans that executed cleanly (pipeline/graph_utils.py), which a sub-query stopped at execute.before never did, and its key is the decomposer's intent text, which is model output and can change. So:
    4. Generated path. The run takes the request's decomposition instead of calling the resolver and decomposer. Each datasource in it is checked with scope.reaches_datasource() as the resolver would, and datasources.after is not called (there is no routing, as on the verified path). The approved sub-query's planner step returns the pinned plan with plan_source="approved", as a cache hit returns a cached one; other sub-queries plan as usual. The pinned plan still goes through plan.after, the validator and the generator, so a plan the policies or the code no longer accept is refused like any other. An approved plan is never written to the plan cache.
    5. Verified path. The curated matcher runs the request's verified query with its bound params, with no matching call.
    6. The approval is checked by the engine, not the hook. When a hook answers NeedsApproval at execute.before, the runner looks for an Approval whose request has the same hook and datasource and whose sql_sha256 equals the hash of the SQL just generated, and accepts it only if: the engine's recomputation of the request's id matches (the request was not edited); the request's question, asker_user_id and asker_tenant_id are this run's; and by holds one of the roles the hook is configured with (approver_roles, by default policies.admin_roles), not the roles the request lists. An accepted approval counts as Allow: hook.decision is published with decision: "approved" and the approver, and the next hook at the point still runs. The hook also sees ctx.approvals, so a hook that wants a stricter rule can apply it.
    7. Different SQL asks again. If the regenerated SQL's hash differs (the generator changed, or a plan.after hook changed the plan), the run ends needs_approval again with the new SQL: an approval never covers SQL nobody saw.

    Built: the shapes on the result (A0)

    ApprovalRequest, Approval and VerifiedRef (id, params) are in nl2sql/hooks/approval.py, and RunStop in nl2sql/limits.py; all are exported from nl2sql. QueryResult.status is a RunStatus (success, plan_only, error, needs_approval, stopped, and needs_clarification, reserved for Wave B), or None when nothing ran and nothing failed (0.6's ""). result_from_state reads the state's approvals_needed and stop, and sets the status from them before looking at errors, so H2 and E3 put those keys in the state and touch no result code. The error codes HOOK_DENIED, HOOK_FAILED, NEEDS_APPROVAL, RUN_LIMIT_REACHED and QUESTION_TOO_BROAD (never retried), JOIN_KEY_TYPE_MISMATCH and JOIN_FAN_OUT (retried) and JOIN_KEY_UNCONVERTED and ALL_NULL_COLUMN (warnings) are in ErrorCode; DECLARED_AHEAD in test_boundary_tidy_ups.py lists each with the PR that raises it, which takes it off the list.

    Votes and fusion

    Retriever.route(question, datasource_ids, explain) -> list[RouteCandidate] replaces retrieve_datasource_candidates. It runs five searches over the live builds of the datasources the caller's scope reaches (the scope filter moves before the search, so a denied datasource never even ranks), and each search ranks datasources by their best entry:

    Signal Search
    description schema.datasource, exact over every datasource (as today)
    examples schema.datasource_example, top VOTE_K
    curated curated.verified_query, top VOTE_K
    tables schema.table across every datasource, top VOTE_K
    columns schema.column across every datasource, top VOTE_K

    The ranks are fused with reciprocal rank fusion (D28):

    score(ds) = sum over signals s:  1 / (RRF_K + rank_s(ds))

    where rank_s(ds) is len(ranked_s) + 1 for a datasource signal s did not rank (amended after review: otherwise merely having entries of a type is a vote).

    VOTE_K = 20 and RRF_K = 60 (the value the RRF literature uses) are constants on Retriever, beside FETCH_MULTIPLIER and LAMBDA_MULT, until the routing suite shows a reason to tune them.

    Then the candidates are the top candidates by score, dropping any whose best entry similarity is under floor_ratio times the most similar candidate's (amended after review: a floor on the fused score never fires).     The join-key type check

    A join or compare combine group joins two sub-queries' results in the aggregator on its join_keys (aggregation/engines/polars_duckdb.py, a polars join). Today nothing checks that both sides of a key have the same kind of type, so a text customer_id from one database joined to an integer from another fails in the aggregator (AGGREGATOR_FAILED, terminal) or matches nothing (B30).

    A validator check alone cannot fix that case. The plan has no cast (there is no CAST in ALLOWED_FUNCTIONS, and nothing in ast_planner/schemas.py), and when one database stores the key as text there is no numeric column for the model to pick instead: a "type mismatch, try again" would turn one terminal failure into three wasted retries and then another. So the fix is in two parts (D30):

    1. The decomposer declares the type. DecomposerResponse's validator requires that each JoinKeyPair.left and .right names a column in the expected_schema of its side's sub-query, with a dtype, and that the two dtypes can be coerced to each other (the table below). A violation is a ValueError, which parse-and-retry feeds back to the model. The decomposer node then marks those columns as join keys on its own copy of each SubQuery: ExpectedColumn.join_key is excluded from the model's tool schema (SkipJsonSchema), so the model can never set it.
    2. The aggregator coerces. Before the join, the engine's aggregator casts both sides of each key to the declared dtype in polars, non-strictly. A value that does not convert becomes null, does not match, and is counted in a JOIN_KEY_UNCONVERTED warning ("3 of 412 support.customer_ref values are not numbers and joined nothing"). This is engine-side compute on result frames, so no dialect is involved.
    3. The validator rejects only what cannot be coerced. In LogicalValidatorNode._validate_static, for each select item that is a join key and a plain column reference, the column's data_type from the snapshot is parsed with sqlglot.exp.DataType.build(data_type, dialect=<the adapter's>) and put in a category: number, text, temporal, boolean, or other. Against the declared dtype:
    Column \ declared number text temporal boolean
    number ok ok (formatted) reject ok (0 and 1)
    text ok (parsed) ok ok (parsed) ok (parsed)
    temporal reject ok (formatted) ok reject
    boolean ok ok reject ok

    A rejected pair is JOIN_KEY_TYPE_MISMATCH, a retryable ERROR that asks for another column, never a cast: "The join key order_date is declared a date, but Orders.OrderId is a number.     10. Schema drift: measure first

    The owner wants drift captured and measured before anything acts on it. Nothing here re-indexes or schedules (D31).

    engine.index.check()

    engine.index.check(datasource_ids=None) -> list[DriftReport]

class DriftReport(BaseModel):
    datasource_id: str
    status: Literal["unchanged", "drifted", "not_indexed", "failed"]
    live_version: str | None          # the build pointer's schema version
    checked_at: datetime
    diff: SchemaDiff | None           # live database against the live build
    impact: DriftImpact | None
    error: str | None

    For each datasource it reflects the live database with the datasource's IndexScope (adapter.fetch_schema_snapshot, no profiling: profile: catalog for the check), fingerprints it with generate_schema_fingerprint, and compares it with the fingerprint of the snapshot the live build pointer names. Equal fingerprints are unchanged; otherwise the diff and impact are computed and schema.drifted is published with detected_by: "check". Nothing is stored and nothing is rebuilt. nl2sql index --check prints the reports and exits 0 when nothing drifted, 1 when something did, 2 when a check failed, so a cron job or CI step can act on it.

    The diff

    class ColumnChange(BaseModel):
    table: str; column: str
    changes: dict[str, tuple[Any, Any]]     # "type", "nullable", "pk": (old, new)

class SchemaDiff(BaseModel):
    datasource_id: str
    from_version: str
    to_version: str | None                  # None: the live database
    tables_added: list[str]; tables_dropped: list[str]
    columns_added: list[ColumnRef]; columns_dropped: list[ColumnRef]
    columns_changed: list[ColumnChange]
    foreign_keys_added: list[str]; foreign_keys_dropped: list[str]
    engine_type: tuple[str, str] | None     # (old, new) when the adapter type changed
    def is_empty(self) -> bool: ...

    It compares exactly what the fingerprint covers (schema/fingerprint.py): table and column names, types, nullability, primary keys, foreign keys, and the snapshot's engine_type, which the diff reports as engine_type: tuple[str, str] | None (a datasource whose type changed). The fingerprint also covers datasource_id, which is the same on both sides of any diff, so: for two snapshots of one datasource, diff.is_empty() is true exactly when the fingerprints are equal; a property test holds that. A rename is a drop and an add: there is no reliable way to tell a rename from a drop without asking someone.

    Stored with the new version. When a build stores a snapshot whose fingerprint differs from the version it replaces, the orchestrator computes the diff and stores it beside the new version, then publishes schema.drifted with detected_by: "build". A version whose structure did not change (only statistics did) gets no diff. StateStore gains:

    def put_schema_diff(self, diff: SchemaDiff) -> None: ...                       # keyed by datasource and to_version
def get_schema_diff(self, datasource_id: str, schema_version: str) -> SchemaDiff | None: ...

    so the store kind moves to interface version 2 (the other three stores only declare it), and the sqlite store adds migration 4, a schema_diffs table that keep_snapshots prunes with its version. The diff's model lives in nl2sql_sdk.schema beside SchemaSnapshot. The version moves for all four slots, not only the state store, because the registry has one version per kind (INTERFACE_VERSIONS["store"] in registry.py) and the four slots share the nl2sql.stores group; a version per slot would be a second mechanism for one method.

    11. Answer sanity checks

    Cheap checks after a sub-query runs, before the aggregator. They live in pipeline/nodes/executor/sanity/, which takes in today's value_check.py. Every probe is a sqlglot expression built from the plan and rendered by the adapter (render_sql or its dialect), bounded by the datasource's row limit, and skipped for a table the caller's scope denies, as value_check.py does today. A check that fails to run reports nothing.

    Check When it runs Detects Then (D32)
    Missing value (exists) An empty result filtered on a string literal The column has no such value. With sample values in the snapshot the closest is taken from them with no query; otherwise from today's bounded DISTINCT probe. A close value and a retry left: retried once (VALUE_NOT_FOUND, ERROR). Otherwise a warning.
    Join fan-out The plan joins a table on a key that is not unique on the other side (known from the snapshot's primary and foreign keys) and aggregates SUM, AVG or COUNT over a column of the one side. This includes one table joined to two others on their many side (a many-to-many sum), which is the same probe per many side. A probe over the plan's FROM, joins and WHERE: COUNT(*) against COUNT(DISTINCT <one side's primary key>). More rows than keys confirms that each row was counted several times. Under COUNT, confirmed with a retry left: retried once (JOIN_FAN_OUT, ERROR), telling the planner to count distinct keys, which the plan can say (Expr.distinct). Under SUM or AVG: a warning only, since the repair (aggregate the many side first) needs a derived table the plan cannot express; splitting such a question in the decomposer is a Wave B idea. Otherwise a warning.
    All-null column A result with rows A result column whose every value is null: usually an outer join that matched nothing, or the wrong column A warning only (ALL_NULL_COLUMN): no probe, and no reliable fix to suggest

    Retries are counted against settings.pipeline.retries.max, and each check retries at most once per sub-query, as VALUE_NOT_FOUND does. A verified query is not checked: a person wrote its SQL. settings.pipeline.sanity_checks: true turns them all off when false.
