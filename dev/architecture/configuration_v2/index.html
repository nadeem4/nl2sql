    Configuration v2 and the extension registry (Phase 1 design)

    Status: built

    This page is the design for Phase 1 of the redesign, which ships as release 0.5. Every pull request in the PR plan is built, and each added a "Built" note to the sections it built and updated the reference pages it touched. PR 13 completes Phase 1. The Configuration pages describe the 0.5 config.

    Principles

    There are no users yet, so nothing we change can break anyone. This design aims to be correct, not compatible:

    • No compatibility code. There are no old names, aliases, shims, deprecation warnings or legacy code paths kept for compatibility. 0.5 reads only the new config. There is no nl2sql config migrate command, only a mapping table in the docs.
    • The right shape, not the smallest diff. Where today's shape is wrong, this page gives the right one and deletes the old. That covers the facade, the settings global, the config models, the CLI flags, the internals the playground and the API reach into, and the names of methods, fields and environment variables.
    • No over-engineering. Ship only what the product needs in 0.5. Anything that can wait for a later phase does.
    • Per-engine config, passed explicitly. The fresh review suggested building today's process-global settings from the new config and leaving the 43 modules that read it alone. That was a compromise to keep the change small. Judged on correctness, the right design is an engine that owns its config and passes it down, with no process-global settings, so two engines in one process never share anything. Phase 1 gets there in staged pull requests, and each one stays green.

    Owner decisions

    The owner answered the six questions this design left open. Each one is written into the section it affects:

    # Decision Where
    1 nl2sql-api settings go in an api: section of nl2sql.yaml, typed by an Api model. The engine ignores it, and nl2sql-api reads engine.config.api. The NL2SQL_API_* variables are removed. api
    2 Only the entry points load .env. The CLI, nl2sql-api and the demo load the .env next to nl2sql.yaml without overriding variables that are already set. The library never reads .env and never writes os.environ. Environment variables
    3 The constructor never connects. The entry points call engine.check(), and required: true is enforced there. Lifecycle
    4 The S3 and ADLS result backends are deleted now. The Phase 2 results-store interface brings remote stores back. storage
    5 nl2sql setup is removed in 0.5. nl2sql init replaces it, and the guided flow comes in Phase 4. CLI
    6 The LLM can be replaced at runtime. engine.llm.replace(LLM(...)) and an admin-only PUT /api/v1/settings/llm do it. The swap is atomic and logged, LLM clients are cached per engine, and the plan cache key includes the planner's model. Replacing the LLM at runtime

    Two rules from earlier decisions apply throughout:

    • Every component works the same way: a small interface, the built-ins we ship, plugin packages people install, and their own code registered in memory.
    • The engine is the product. The CLI, nl2sql-api and the playground are consumers. Anything one of them needs that another caller could also need becomes an engine method.

    1. Goals and non-goals

    What ships in 0.5

    Goal What it means
    One typed config nl2sql.yaml and its split files build one Config object. Building it in code gives exactly the same object.
    A short list of environment variables Only NL2SQL_CONFIG, NL2SQL_LOG_LEVEL and the provider key variables are read directly. Everything else is written in the YAML, as ${env:VAR} where it should come from the environment.
    A registry, as a value Registry.default() maps names to code for adapters, LLM providers, embeddings providers and secret providers. Plugins add names through entry points, and your own code adds them with add_* or a decorator.
    A defined loading order Discover names, eagerly load and validate what the config uses, connect lazily, and report readiness with engine.check().
    A light import import nl2sql loads no database driver, chromadb, onnxruntime, textual or opentelemetry. A test enforces this.
    A clean facade run_query and stream_query at the top level, and everything else in noun namespaces. engine.context, the duplicate methods and the sub-API classes are removed.
    A runtime LLM switch engine.llm.replace() and PUT /api/v1/settings/llm swap the LLM atomically and log who changed what. LLM clients are cached per engine.
    No process globals Settings, the embeddings cache and the secret manager belong to one engine, and nothing writes os.environ. Two engines can run in one process.
    The SDK renamed nl2sql-adapter-sdk becomes nl2sql-sdk (nl2sql_sdk). It holds the adapter and secrets interfaces.
    CLI on one flag A single --config, plus nl2sql init and nl2sql config check.

    2. The config files

    Built: the models and load_config (PR 2)

    The models, load_config, ConfigError, load_env_file and the nl2sql.testing.config.make_config test helper are in nl2sql.config. The engine is built from them since PR 7a, and they are exported from nl2sql. Since PR 7b the Configuration pages are the reference. Building them settled these details:

    • In Settings, the schema group is the attribute schema_ in Python, because schema would shadow a pydantic method. The YAML key is schema.
    • Policies.allow_all() (the shorthand) and the allow_all field share a name: the shorthand answers on the class, the field on an instance. default_role must name one of the roles.
    • A secret provider's own keys (everything but id and type) keep their references, like a datasource's connection, until the provider's config_model (PR 4) says which of them are secrets.
    • Outside secret fields and connection, only ${env:...} resolves at load. Another provider's reference there is an error that names the field.
    • datasources is required in code as well as in the file; [] is enough.

    The table of contents

    nl2sql.yaml is short. nl2sql init writes it with each section in its own file:

    # nl2sql.yaml
version: 2
datasources: { file: datasources/ }      # a folder, one file per datasource
llm:         { file: llm.yaml }
embeddings:  { file: embeddings.yaml }
policies:    { file: policies.yaml }
storage:     { file: storage.yaml }
curated:     { file: curated.yaml }      # optional
secrets:     { file: secrets.yaml }      # optional
settings:    { file: settings.yaml }     # optional
api:         { file: api.yaml }          # optional, read by nl2sql-api only

    A small project can write every section inline instead. This file builds the same Config as the split layout above:

    version: 2
datasources:
  - id: shop
    type: sqlite
    connection: { database: shop.db }
llm:        { provider: anthropic, model: claude-sonnet-5-5 }
embeddings: { provider: local }
policies:   { allow_all: true }
storage:    { path: .nl2sql }
    Section Required Pydantic class Notes
    version yes Literal[2] Anything else, or a missing version, is an error that links to the mapping table.
    datasources yes list[Datasource] May be an empty list. The apps add datasources at runtime.
    llm yes LLM Flat: the keys are the LLM fields.
    embeddings yes Embeddings {provider: local} is a complete section.
    policies yes Policies {allow_all: true} is a complete section.
    storage yes Storage {path: .nl2sql} is a complete section.
    curated no Curated Absent means curated answers are off.
    secrets no Secrets The env provider is always available without it.
    settings no Settings Tuning knobs. Every field has a default.
    api no Api nl2sql-api's own settings. The engine validates it and never reads it.

    The five required sections are explicit choices. There is no hidden default for where data lives, which embedder runs, or who may read what. Each one fits on one line, and nl2sql init writes all five.

    glossary and evals are not Phase 1 sections. The root model forbids unknown keys, so writing one in 0.5 is an error.

    file: includes

    Rule Detail
    Shape A section is either inline, or exactly {file: <path>} with no other keys.
    Relative paths The path is relative to nl2sql.yaml, not to the working directory.
    One level Only nl2sql.yaml may include. An included file holds the section's body and cannot include anything itself, so there are no chains and no cycles.
    No version Only nl2sql.yaml has version:.
    Datasource folder datasources: {file: datasources/} names a folder. Every *.yaml in it, sorted by name and not recursive, holds one datasource. id may be left out and defaults to the file name without .yaml. If it is given, it must equal the file name, so the owner of sales.yaml owns the sales datasource.
    Datasource file datasources: {file: datasources.yaml} names a file whose body is the list.
    No interpolation in paths file: values are literal. ${...} there is an error.
    Each file once Including the same file twice is an error.

    Each team can then own its own database's file:

    # datasources/sales.yaml   (id defaults to "sales")
type: postgres
description: Orders, customers and revenue for the EU shop.
connection:
  host: db.internal
  database: sales
  user: nl2sql
  password: "${env:SALES_DB_PASSWORD}"
limits: { row_limit: 1000, timeout_ms: 8000 }
preferred_tables: [public.revenue_daily]
domains: [revenue, customers, orders]
sample_questions:
  - What was revenue by region last quarter?
  - Which customers placed the most orders this year?

    ${provider:key} interpolation

    The grammar is today's: ${env:SALES_DB_PASSWORD}, ${vault:db/sales#password}. The first part is a secret provider's id. env is built in and always available.

    Rule Detail
    Whole value only A reference is the entire string. "postgres://${env:U}@db" is an error. There is no default syntax (${env:X:-y}).
    Secrets resolve late Fields of type Secret (every api_key, the secret providers' credentials) and every value under a datasource's connection hold the reference, not the value. They are resolved when the component is built, so engine.config, logs and errors never contain a plaintext secret. A value written literally (or given in code, as the demo gives its key) stays a plain str the engine reads, and repr/str print it as **********: a Secret field always, and under connection or a secret provider's settings, a key whose name contains password, secret, token or api_key. A reference prints as written. A validation error never echoes its input (hide_input_in_errors).
    Everything else resolves at load Any other field, for example storage.path: "${env:NL2SQL_DATA_DIR}", is resolved by load_config. A missing variable is a load error that names the field.
    Inside secrets: Only ${env:...} is allowed, because one provider cannot depend on another.

    Strict keys and "did you mean"

    Every model sets extra="forbid" and frozen=True. An unknown key is an error, and it suggests the closest known key (difflib.get_close_matches, cutoff 0.6). The same applies to names the registry resolves (type:, provider:), where the suggestion comes from the installed names.

    Error messages

    load_config and NL2SQL(...) collect every problem before raising one ConfigError. They do not stop at the first one.

    nl2sql.yaml has 3 problems:

  datasources/sales.yaml → preferd_tables
    Unknown key. Did you mean 'preferred_tables'?

  llm.yaml → provider
    'antropic' is not an installed LLM provider. Did you mean 'anthropic'?
    Installed: anthropic, ollama, openai, openrouter.

  datasources/sales.yaml → type: postgres
    The postgres adapter needs the module 'psycopg2', which is not installed.
    Fix: pip install "nl2sql-engine[postgres]"

    The rules: - Each problem gives the file, then the path inside it (file → a.b[2].c). - What is wrong is said in one sentence, followed by a Fix: line when the fix is known. - A secret is shown as its reference (${env:SALES_DB_PASSWORD}), never as its value. - A 0.4 file gets one specific message: "configs/datasources.yaml is a 0.4 config file (version: 1). 0.5 reads nl2sql.yaml: see architecture/configuration_v2."

    The sections

    All classes live in nl2sql.config and are exported from nl2sql. Field names are the YAML keys.

    datasources: Datasource

    Field Type Default Was (0.4)
    id str the file name in a folder, otherwise required id
    type str required, unless adapter is given connection.type
    description str \| None None description
    connection dict[str, Any] {} connection without type. It is validated by the adapter. Typed models per adapter arrive in Phase 2.
    limits Limits Limits() options.row_limit, options.statement_timeout_ms, options.max_bytes and the top-level fold
    preferred_tables list[str] [] preferred_tables
    sample_questions list[str] [] sample_questions.yaml, keyed by datasource
    domains list[str] [] new: a routing hint written by people. The domains generated at indexing are separate and stored with the index. Routing does not read it yet (a later phase).
    required bool False new: engine.check() fails if this datasource cannot connect
    adapter adapter object None new: pass a built adapter instead of type (code only)

    Limits has row_limit: int | None, timeout_ms: int | None and max_bytes: int | None. The options: bag and the rule that "the lower of the two wins" are removed, so there is one place to set each limit.

    llm: LLM (flat)

    # llm.yaml
provider: anthropic
model: claude-sonnet-5-5
temperature: 0
# api_key is optional: without it the provider's standard variable
# (ANTHROPIC_API_KEY) is read. Write it to use another name:
# api_key: "${env:TEAM_ANTHROPIC_KEY}"
agents:
  ast_planner:         { model: claude-opus-5-5 }
  answer_synthesizer:  { provider: openai, model: gpt-5.4 }
  profiler:            { model: claude-haiku-5 }   # indexing_enrichment until 0.8
prices:
  my-finetune: { input: 0.2, cached_input: 0.1, output: 0.6 }
    Field Type Default Was (0.4)
    provider str \| None required, unless model is an object default.provider
    model str \| BaseChatModel required default.model
    temperature float \| None 0.0 default.temperature (null still means "send none")
    api_key Secret \| None None, which means the preset variable default.api_key
    base_url str \| None None default.base_url
    agents dict[AgentName, AgentLLM] {} agents
    prices dict[str, Price] {} LLM_PRICES (JSON in an env var)

    AgentLLM has the same five fields as the top level (provider, model, temperature, api_key, base_url), all optional. An agent takes each field it sets and inherits the rest. Inheritance is decided by which fields were set (model_fields_set), so temperature: null on an agent still means "send none". AgentName is a closed set of the node names: curated_matcher, datasource_resolver, decomposer, ast_planner, refiner, answer_synthesizer and profiler (indexing_enrichment until 0.8). The concatenated 0.4 keys (astplanner, answersynthesizer) and the name: field are gone, along with the LLM_AGENTS mapping between the two spellings. Price has input, output, and optionally cached_input and cache_write, as LLM_PRICES does today.

    embeddings: Embeddings

    Field Type Default Was (0.4)
    provider str \| None required, unless instance is given EMBEDDING_PROVIDER (default was openai)
    model str \| None the provider's default EMBEDDING_MODEL
    api_key Secret \| None the provider's standard variable OPENAI_API_KEY via Settings
    instance LangChain Embeddings object None new (code only)

    policies: Policies

    The semantics are today's, written in YAML instead of JSON. allow_all, default_role and admin_roles are the small additions that the one-line section and the move of NL2SQL_API_ADMIN_ROLES need.

    # policies.yaml
default_role: viewer
admin_roles: [admin]
refusal_names_tables: false
roles:
  admin:
    description: Every table in every database
    allowed_datasources: ["*"]
    allowed_tables: ["*"]
  analyst:
    description: Sales, except the audit schema
    allowed_datasources: [sales]
    allowed_tables: ["sales.public.*"]
    Field Type Default Was (0.4)
    allow_all bool False new: every caller may read everything (local and dev use). It cannot be combined with default_role or roles.
    default_role str \| None None new: the role used when the entry point gives none. Without it, no role means a refusal, as today.
    admin_roles list[str] ["admin"] NL2SQL_API_ADMIN_ROLES
    refusal_names_tables bool False RBAC_REFUSAL_NAMES_TABLES
    roles dict[str, Role] {} roles in policies.json

    Role has description, allowed_datasources and allowed_tables, with today's meaning and pattern rules. The redundant role: field, which repeated the key, is removed. Policies.allow_all() is the code shorthand. The allow/deny globs replace these names in Phase 2, once rather than twice.

    storage: Storage (path only)

    # storage.yaml
path: .nl2sql          # or "${env:NL2SQL_DATA_DIR}" in Docker
    Field Type Default
    path Path required. Relative to nl2sql.yaml in a file, and to the working directory in code.

    Today's stores move under it:

    Store 0.4 location and variable 0.5 location
    Vector index (chroma) ./chroma_db (VECTOR_STORE), collection nl2sql_store (VECTOR_STORE_COLLECTION) <path>/index/. The collection name becomes an internal constant.
    Schema snapshots, plan cache, feedback data/schema_store.db (SCHEMA_STORE_PATH) <path>/state.db
    Run traces traces/ (TRACE_DIR) <path>/traces/
    Result files ./artifacts (RESULT_ARTIFACT_BASE_URI) <path>/results/

    The S3 and ADLS result backends (RESULT_ARTIFACT_BACKEND=s3|adls and their settings) are deleted in 0.5 (owner decision 4). They were untested and unreachable from the new config. The Phase 2 results-store interface brings remote stores back as built-ins or plugins.

    In Phase 2, index, state, traces and results become optional sub-blocks, each with a type. A config with only path stays valid.

    secrets: Secrets

    # secrets.yaml
providers:
  - id: vault
    type: hashicorp
    url: https://vault.internal:8200
    token: "${env:VAULT_TOKEN}"

    providers: list[SecretProviderConfig]. type is resolved through the registry (env, aws, azure and hashicorp are built in; 0.4's hashi is renamed), and each provider validates its own block with its config_model. The id env is reserved. A provider that fails to configure fails startup and names secrets.providers[i], instead of being logged and swallowed (bug B10). The fallbacks to VAULT_ADDR, VAULT_TOKEN and AZURE_KEYVAULT_URL are removed: write the field, with ${env:...} if the value comes from the environment.

    curated: Curated

    The body is today's curated.yaml without version: datasources: {<id>: {verified_queries: [...], metrics: [...]}}. If the section is present, curated answers are on. If it is absent, they are off. That replaces CURATED_ENABLED, and the eval tier that runs without curated answers builds its engine from cfg.model_copy(update={"curated": None}).

    settings: Settings

    These are the tuning knobs that were environment variables. Every field has a default, so the section is optional.

    # settings.yaml (every value shown is the default)
tenant_id: default_tenant
pipeline:
  timeout_s: 60
  plan_cache: true
  strict_columns: true
  today: null                 # pin the run date: 2013-12-31
  retries: { max: 3, base_delay_s: 1.0, max_delay_s: 10.0, jitter_s: 0.5 }
retrieval:
  full_snapshot_max_tables: 15
results:
  row_limit: 100000
  fetch_batch_size: 10000
  preview_rows: 20
traces:
  mode: on_failure            # off | on_failure | always
  sample_rows: 50
  max_field_chars: 20000
schema:
  max_versions: 3
  version_mismatch: warn      # warn | fail | ignore
curated:
  match_top_k: 5
  match_floor: 0.6
feedback:
  enabled: true
observability:
  exporter: none              # none | console | otlp
  otlp_endpoint: null

    Each group is its own frozen model (PipelineSettings, RetrySettings, RetrievalSettings, ResultSettings, TraceSettings, SchemaSettings, CuratedSettings, FeedbackSettings, ObservabilitySettings), with today's validation (for example match_floor between 0 and 1).

    api: Api

    These are nl2sql-api's own settings (owner decision 1). The class lives in nl2sql.config, so the file gets the same strict validation, ${env:} rules and nl2sql config check as every other section. The engine never reads it, and nl2sql-api reads engine.config.api. Without the section, nl2sql-api uses the defaults: no role source, so admin routes answer on loopback only, as today.

    # api.yaml
role_header: X-NL2SQL-Role      # a header a trusted proxy sets on every request
role: null                      # or one static role for every request
trust_body_role: false          # accept "role" in the request body (dev only)
cors_origins: [https://app.example.com]
    Field Type Default Was (0.4)
    role_header str \| None None NL2SQL_API_ROLE_HEADER
    role str \| None None NL2SQL_API_ROLE
    trust_body_role bool False NL2SQL_API_TRUST_BODY_ROLE

    4. Creating the engine

    Built: the runtime from Config (PR 7a)

    NL2SQL(config, *, registry=None), NL2SQL.from_config(), NL2SQL.demo(), check(), close() and the context manager are built. Runtime.from_config(cfg, registry) (nl2sql/runtime.py) replaces NL2SQLContext and nl2sql/context.py; CheckReport, DatasourceStatus and EngineNotReady are in nl2sql/check.py. Config, load_config and the section classes are exported lazily from nl2sql. Building it settled these details:

    • What fails where. Everything that can be known without a connection is one ConfigError from the constructor: an unknown or uninstalled name, a secret provider that cannot start (bug B10), an adapter that rejects its connection settings or a reference that does not resolve, an embeddings provider without its key, and curated answers that do not match the datasources. A datasource that cannot connect is check()'s: failed at stage connect. test_connection() returns a bool, so the reason is generic until the SDK v2 stages (Phase 2). A problem names nl2sql.yaml (or Config when built in code) and the path inside the config (datasources[1].type); which split file a section came from is not tracked yet.
    • Relative files. load_config records the folder of nl2sql.yaml as Config.folder (a private attribute that copies keep and equality ignores). The engine passes it to every adapter as base_dir, and the SQLite and DuckDB adapters read a relative database from there (BaseSQLAlchemyAdapter.local_path). The adapters' connection models no longer have a type field: type is on the Datasource.
    • One secret provider shape. SecretProviderConfig is the one in nl2sql.config (id, type and the provider's own keys, kept as written). The provider's config_model validates the block when the engine builds the provider, after resolving its ${env:...} values. nl2sql/secrets/models.py and the module-level secret_manager are deleted; each engine builds its own SecretManager(registry).
    • Per engine. The embedder is built once from embeddings through the registry, or is the instance given; EmbeddingService is deleted. The LLM is the engine's LLMSet, built from the llm section through its LLMClientCache (PR 9, Replacing the LLM at runtime). Policies.allow_all and default_role are applied by RBAC.
    • Stores. The index is <storage.path>/index/ (collection nl2sql_store, a constant), the schema store <storage.path>/state.db, traces <storage.path>/traces/ and results <storage.path>/results/. The S3 and ADLS result backends and their settings are deleted.
    • Datasources. engine.add_datasource(Datasource) (since 10a engine.datasources.add) builds the adapter (not connected) and swaps in a new engine.config under the engine's lock. Indexing reads a datasource's description and sample questions from its Datasource, so one added in code keeps both (bug B9).
    • The 0.4 entry points (nl2sql._legacy, NL2SQL._legacy()) lived for one PR; PR 7b deleted them with the 0.4 files.
    • Tests. nl2sql.testing.config.make_demo_config(folder) is make_config with the demo's databases and roles; the integration and end-to-end fixtures build their runtime from it.

    report = engine.check()

    Method What it does
    NL2SQL(config, *, registry=None) Loads and validates: resolves every name, imports only those components, checks interface versions and driver modules, builds the secret manager, adapters (not connected), LLM clients (no call) and stores. Raises one ConfigError with every problem. It never connects to a datasource or calls a model (owner decision 3).
    NL2SQL.from_config(path=None, *, registry=None) NL2SQL(load_config(path), registry=registry).
    engine.check() -> CheckReport Connects to each datasource and records ready or failed(stage, reason, fix). A failed datasource is marked unavailable and left out of routing. It also checks that every agent's API key resolves (no model call) and reports the index status (index.health()). It raises EngineNotReady if a required: true datasource fails, or if datasources are configured and none is ready. It is safe to call again.
    engine.close() Disposes adapter pools and closes the state store and the vector store client. The engine cannot be used afterwards. Calling it twice is fine.
    __enter__ / __exit__ with support. __exit__ calls close().
    engine.config The current frozen Config. Secrets appear as references only. It changes only through datasources.add/remove and llm.replace.

    Startup policy belongs to the entry points. The CLI, nl2sql-api (in its lifespan, before it accepts requests) and the playground call engine.check() straight after construction. They refuse to start on EngineNotReady, and they start degraded, printing the report, when an optional datasource fails. A Python caller decides for itself. Without check(), a broken datasource fails the first query that targets it, with its reason. Building an engine therefore stays cheap and has no side effects for tests, nl2sql config check and notebooks.

    Replacing the LLM at runtime

    Built: the LLM client cache and llm.replace (PR 9)

    engine.llm.replace(llm, *, by=None, via="python") -> LLMChange is built (Runtime.replace_llm in nl2sql/runtime.py), with LLMSet and LLMChange in nl2sql/llm/llm_set.py and LLMClientCache in nl2sql/llm/client_cache.py. LLMRegistry is now the per-engine holder of the current set and the cache; the nodes still ask it for their client by name. Building it settled these details:

    • The entry point. replace takes via alongside by, so the entry point (python, api, playground) is known when there is no user. PUT /api/v1/settings/llm (PR 10a) replaced POST /llm and configure_llm.
    • Keys. replace fails with ConfigError when an agent's API key does not resolve (llm.api_key, llm.agents.<agent>.api_key). At construction a key that does not resolve is still check()'s to report, and using that agent raises the reason.
    • Clients are built up front, at construction and on replace, so the key is read then: a key set in the environment later is used only once the LLM is set again.
    • Reading the set once. run_with_graph pins the current set to the run (LLMRegistry.begin_run, a context variable read while the graph is built) and releases it when the graph finishes, which a timed-out run has not yet done. The trace records the run's set.
    • Closing. The built-in wires build ChatOpenAI and ChatAnthropic, which share their library's process-wide connection pool, so there is no HTTP client of their own to close: closing calls the client's close() when it has one (a provider registered in code), and is otherwise dropping the reference.
    • The plan cache key carries the planner as provider/model, the effective one for the run (a caller's per-request model included); a model object is Class/model.

    Owner decision 6 keeps a runtime model switch. Changing the model by hand is something both the playground and an operator need.

    The entry points

    Caller How
    Python engine.llm.replace(llm: LLM, *, by: UserContext \| None = None) -> LLMChange
    nl2sql-api PUT /api/v1/settings/llm, admin only (require_admin). The body is the llm section as JSON, the same shape as llm.yaml. It replaces POST /llm. It returns the LLMChange with no keys.
    Playground The settings panel calls engine.llm.replace(...).

    Validation. The new section is validated exactly like llm.yaml. The same LLM model runs with extra="forbid" and "did you mean", the provider names are resolved through the engine's registry (checking interface version and find_spec), and every agent's key reference is resolved. A request that fails changes nothing and returns the same ConfigError text, as HTTP 422 from the API. No model is called during validation.

    The swap is atomic. - The runtime holds one immutable LLMSet, which maps each agent to its client and resolved settings. - replace builds the new LLMSet completely, then swaps one reference under the engine's lock, along with engine.config (llm is replaced, and nothing else changes). - A run reads the reference once, when it starts. In-flight runs finish on the old set, and every run that starts after the swap uses the new one. No run ever mixes the two.

    It is not persisted. The file on disk is not rewritten, so a restart returns to llm.yaml. Saving the change explicitly is out of scope for 0.5. The playground already writes its own llm.yaml for the next start, and keeps doing so as a separate step after replace succeeds.

    Every swap is logged. One INFO log line, and one audit record through the engine's event_logger. That stub becomes the audit observer, and the record becomes the llm.changed event, when the Phase 3 event bus lands. The record holds: - who: by.user_id and by.roles when known, otherwise the entry point (api, playground, python); - each agent whose effective provider or model changed, as old and new; - never a key, a key reference or a header value.

    INFO nl2sql.llm: LLM replaced by user=u42 roles=[admin] via api:
  default: openai/gpt-5.4 -> anthropic/claude-sonnet-5-5;
  ast_planner: openai/gpt-5.4 -> anthropic/claude-opus-5-5

    Clients are cached per engine. LLMClientCache is owned by the runtime and is not a global. It also serves initial construction. - The key is the agent's resolved client settings: provider, model, base_url, temperature, and every other client field the agent model has (Phase 2 adds max_tokens, timeout_s, max_retries, seed and headers, and the key covers them automatically because it is built from the model's fields). - Secrets are resolved but never stored in the key. The resolved API key (and any secret header) enters the key only as a SHA-256 digest, and the key's string form, used in logs and debugging, prints the digest prefix only. - Sharing. Agents whose settings are equal share one client, so seven agents on one model build one client. Swapping back to an earlier LLM reuses the cached clients instead of building new ones. - Bounded. An LRU of 16 entries. A client evicted from the cache is closed (its HTTP client's close()) once no LLMSet refers to it any more, so an in-flight run on the old set is never cut off. engine.close() closes them all.

    The plan cache key includes the planner's model. Today the key is the normalised intent and run date, the datasource and the schema version (pipeline/plan_cache.py). It gains the ast_planner agent's effective provider and model, so after a swap a plan written by another model is never served. Entries from the old model stay in the cache, and swapping back hits them again.

    5. The registry

    Built: the registry (PR 5)

    nl2sql/registry.py holds Registry with default(), empty(), the add_* methods and decorators for the four Phase 1 kinds, names(), and load(kind, name), which imports a name and runs the load-time checks (interface version with the package name, find_spec with the install hint, duplicate entry points naming both packages, "did you mean"). It raises RegistryError; collecting those into a ConfigError is NL2SQL(cfg, registry)'s job, in PR 7a. The built-ins are declared in the four entry point groups. LLMProvider and ResolvedAgent live in nl2sql.llm.providers, EmbeddingsProvider in nl2sql.embeddings. discover_adapters() and nl2sql/secrets/factory.py are deleted: the DatasourceRegistry, the secret manager and nl2sql list-adapters use the registry. Since PR 7a the runtime resolves its LLM providers and builds its embedder through the registry it is given.

    What it is

    A YAML file holds only text. When it says type: postgres or provider: anthropic, something has to turn that name into code. The Registry is that lookup table. It is a value that you pass to the engine, not a global, so two engines (or two tests) never see each other's registrations.

    class Registry:
    @classmethod
    def default(cls) -> "Registry": ...   # built-ins + installed plugins: entry point names only, no imports
    @classmethod
    def empty(cls) -> "Registry": ...     # nothing; for tests and allow-lists

    # chosen kinds in Phase 1: one name per slot
    def add_adapter(self, name: str, cls: type, *, replace: bool = False) -> None: ...
    def add_llm(self, name: str, provider: LLMProvider, *, replace: bool = False) -> None: ...
    def add_embeddings(self, name: str, provider: EmbeddingsProvider, *, replace: bool = False) -> None: ...
    def add_secrets(self, name: str, cls: type, *, replace: bool = False) -> None: ...

    # the same, as decorators
    def adapter(self, name: str): ...
    def llm(self, name: str): ...
    def embeddings(self, name: str): ...
    def secrets(self, name: str): ...

    def names(self, kind: Kind) -> list[str]: ...   # for errors, `nl2sql list-adapters`, the apps
    Rule Detail
    Names only default() lists entry points and imports none of them. A name is imported when an engine's config uses it.
    No hidden global default() builds a new value each call. Only the scan of installed entry points, which is plain data, may be cached.
    Clashes add_* with a name already present raises, unless replace=True. Two installed packages declaring the same name raise when that name is used, naming both packages.
    Objects skip the registry A Datasource(adapter=...), LLM(model=<object>) or Embeddings(instance=...) is used as given.
    Validation order load_config checks only shape: type is a string. Names are resolved by NL2SQL(...) and by nl2sql config check, against the registry passed in. That is why registering on your own registry before building the engine is enough.

    Built: nl2sql init (PR 6)

    Demo and playground

    Built (PR 7b)

    As designed, with these details:

    • The demo writes the llm section to its own llm.yaml rather than building the LLM in code: the playground's settings panel edits that file and reloads the engine's LLMs from it, so the two must agree. In replay and record mode it points base_url at the local replay server or the recording proxy with the placeholder api_key that endpoint takes (replay, proxy); live, it names no key, so the provider's variable is read. A real key is never written into YAML.
    • Keys still reach os.environ in two places until PR 10 and 13: a key from --api-key or the demo's .env, and one saved in the settings panel. --record turns the plan cache off in the engine's own config (settings.pipeline.plan_cache), not through the environment; hosted mode never turned it off, so nothing changes there.
    • What 0.4's .env.demo set is now in the demo's config: demo_config(), and so init --demo (which writes it as settings.yaml), carries settings.pipeline.timeout_s: 300, settings.traces.mode: always and policies.refusal_names_tables: true.
    • --questions-per-minute and --questions-per-session replace the NL2SQL_DEMO_* variables, and NL2SQL_DEMO_HOSTED is gone: --hosted is the only switch.
    • nl2sql demo runs init --demo into nl2sql-demo/ the first time, builds the index if check() reports it missing, then serves the playground on NL2SQL.from_config("nl2sql-demo/nl2sql.yaml").
    • A key the demo is given is written to nl2sql-demo/.env (it was .env.demo) and passed into the LLM it builds. Nothing goes into os.environ.

    Built: keys without the environment (PR 13)

    nl2sql demo --api-key writes the key to the demo's .env and passes it to _build_engine as api_keys (provider -> key), which puts it into the engine's llm section in memory with nl2sql.cli.demo.llm_config.with_api_keys: the top level gets its provider's key unless it names one, and an agent on another provider gets that provider's key, or explicitly none, so it never inherits a key for a provider it does not run on. llm.yaml still never holds a key. A key in .env from an earlier run reaches the engine through load_env_file, as for every entry point; the flag wins over an exported variable because it travels as a value, which the engine prefers to the environment. The settings panel keeps the same api_keys, adds each key saved in it, and passes them with every engine.llm.replace; it shows a key masked from there or from the environment. Hosted mode used to remove the provider key variables from its own environment; it now refuses to start when one is set, since a public server must not hold a key and the demo no longer writes the environment to drop it.

    • Replay mode keeps its local fake server. The demo points the config at it with LLM(provider="openai", base_url="http://127.0.0.1:<port>/v1", api_key="replay") instead of setting OPENAI_API_KEY=replay.
    • PLAN_CACHE_ENABLED=false in hosted mode becomes settings.pipeline.plan_cache: false in the hosted demo's config.
    • CLAUDE.md's rule "never read nl2sql-demo*/ or any .env" stays as it is. Only its mention of .env.demo changes.
