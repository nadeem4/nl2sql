    Phase 2: test bed, storage, providers, policies and adapter SDK v2 (design)

    Status: design

    This page is the design for Phase 2 of the redesign, which ships as release 0.6. Nothing on it is built yet. Each pull request in the PR plan adds a "Built" note to the sections it builds, as Phase 1 did. Phase 1 is described in Configuration v2 and the extension registry.

    Principles

    The Phase 1 principles still hold, and the owner restated them for Phase 2:

    • No users yet, so design it correctly, not compatibly. No shims, no aliases, no deprecation periods. Where a 0.5 shape is wrong, 0.6 replaces it.
    • Never over-engineer. Ship what 0.6 needs. Anything that can wait, does.
    • Prefer extension points over built-ins. A small interface and a way to register your own beats another built-in we have to maintain.
    • No database-specific code outside adapters. The plan says what; the adapter says how.
    • The package is the product. The CLI, nl2sql-api and the playground use the public API only.

    One more rule comes from how Phase 2 was ordered: nothing about a real database is designed from memory. Until now every test ran against SQLite, DuckDB and mocks. Phase 2 builds a test bed with real PostgreSQL, MySQL and SQL Server first, and the adapter work is proven on it.

    Owner decisions

    The owner answered every question this design raised, and confirmed the choices it made on its own. Each answer is written into the section it affects.

    # Decision Where
    1 No Cloud SQL. A stopped Cloud SQL instance still bills its public IPv4 address, so the test bed is one compose file instead, run locally, in CI and on one small GCP VM. The real-database test bed
    2 CI runs the real databases only when they matter: on pull requests that change database-facing code, nightly on main, and on demand before a release. A small gate job that always runs is the required check, so a skipped run passes honestly. The containers run on GitHub's runners. CI: the realdb workflow
    3 The GCP test bed is one small VM running the same compose file, started and stopped on demand, with an ephemeral external IP, no public database port, and access through IAP tunnels. A nightly scheduler job stops it. There are no GitHub-to-GCP credentials: it is run by hand, at least before each release. The GCP VM
    4 SQL Server declares ENFORCES_READ_ONLY false, check() warns, and the docs recommend a login with only db_datareader. Read-only and timeouts, honestly
    5 Two-part policy patterns are rejected, with the fix in the message. Pattern rules
    6 No S3 or ADLS result store in 0.6. The ResultStore interface ships with a docs example; a community plugin can come later. The interfaces
    7 Built-in LLM providers stay minimal: openai, anthropic and openai_compatible. There is no azure_openai; Azure's v1 endpoint, vLLM, LiteLLM and any other OpenAI-style server use openai_compatible with a base_url. openrouter and ollama stay as named presets of openai_compatible: a fixed base_url and key variable, with no code path of their own.     8 Read-only always. There is no per-datasource read_only setting: every adapter makes its session read-only whenever it can. Read-only and timeouts, honestly
    9 Sample values are off by default (index.sample_values: false); the demo turns them on. IndexScope: what gets indexed
    10 Policy patterns match regardless of case, so a deny cannot be dodged by Orders against orders. Pattern rules
    11 A PolicyCheck is called once per user and datasource per run, with no cache across runs. The PolicyCheck extension point
    12 The runtime price table moves to Phase 3 with the cost observer, and the REST routes for Connect a database to Phase 4; Phase 2 ships the package methods. Not in Phase 2

    1. Goals and non-goals

    What ships in 0.6

    Goal What it means
    A real-database test bed PostgreSQL with Pagila, MySQL with Sakila and SQL Server 2022 with AdventureWorksLT, plus a generated schema of 1,200 tables in 20 schemas. One docker-compose.yml runs them locally, on GitHub's runners in CI, and on one small GCP VM started on demand. A realdb pytest marker and fixtures point the same tests at any of them.
    Four stores storage gets index, state, traces and results, each with a type, behind four small interfaces in the SDK. The index's build pointer is the commit, which fixes bug B5. The index has one namespace per embedding model.
    A general LLM provider openai, anthropic and openai_compatible (any server with an OpenAI-style API at a base_url: Azure's v1 endpoint, vLLM, LiteLLM), with openrouter and ollama kept as named presets of it. Each provider declares how it returns structured output, and a malformed answer is retried with the error fed back.
    Embeddings providers local, openai and openai_compatible, base_url on the hosted ones, and a known model and dimension for every embedder.
    Policies, step 1 Allow and deny globs over datasource.schema.table, one Scope object used at every place access is decided, denied tables hidden from the planner, and a PolicyCheck extension point.
    Adapter SDK v2 A typed ConnectionModel per adapter (which also drives a generated form), IndexScope, type-aware profiling with catalog row estimates, honest read-only and timeout capabilities checked against real servers, test_connection that names the failed stage, the SQLAlchemy base made public as an SDK extra, and a conformance kit run against all five built-in adapters.
    Connect a database, in the package engine.datasources.types(), test() and add(): the package methods a Connect-a-database form calls.

    Not in Phase 2

    Snowflake and BigQuery adapters The conformance kit comes first; a community package passes it, then is adopted Later (owner)

    The runtime price table owned by llm/ It belongs with the cost observer Phase 3
    REST routes and forms for Connect a database, datasources.scan() and draft() The package methods ship first; the apps render them Phase 4
    Retrieval limits as settings, incremental re-indexing The wide schema in the test bed measures the problem first After 0.6

    3. The real-database test bed

    Built: the compose file, the realdb marker and the CI workflow (PR T1)

    testbed/ holds the compose file, wide_schema.py, samples.py (the pinned samples with their checksums), passwords.py, the servers' init scripts and gate.py; packages/nl2sql/tests/realdb/ holds the fixtures; and .github/workflows/realdb.yml runs them. Four details differ from the first draft of this section. The passwords have no default: testbed/passwords.py writes random ones to the git-excluded testbed/.env, and CI generates new ones per run, so no password is written in the repository. Pagila is pinned to commit 5ba5a57, because later commits need PostgreSQL 18. The audit schema is a small 21st schema beside the 20 numbered ones that hold the 1,200 tables. datasource() defaults to the server's own sample database (Pagila, Sakila or AdventureWorksLT) and passes other keywords to Datasource, since Datasource.index arrives with B1. The GCP VM and scripts/testbed.py are PR T2. See The real-database test bed.

    What it is

    One file, testbed/docker-compose.yml, defines the whole test bed. The same file runs in three places (owner decision 2):

    Where When Cost
    Your machine whenever you want free
    GitHub's runners (CI) pull requests that change database-facing code, nightly on main, and on demand before a release free; no IP address involved
    One small GCP VM by hand, at least once before each release about $0.07 an hour running; disk only (about $1 to $2 a month) when stopped
    Server Sample database Generated schema
    PostgreSQL 16 Pagila wide (1,200 tables, 20 schemas)
    MySQL 8.0 Sakila wide_s01 ... wide_s20 (MySQL's schemas are databases)
    SQL Server 2022 AdventureWorksLT 2022 wide
    SQLite, DuckDB the conformance kit's own seed, in process, in the unit job —

    The generated schema is loaded on all three servers everywhere, because IndexScope and catalog row estimates are per adapter, and one compose file means one behaviour.

    There is no Cloud SQL. An earlier draft of this page used three Cloud SQL instances; a stopped Cloud SQL instance still bills its public IPv4 address, and a VM running the same compose file is cheaper, simpler and identical to CI.

    The sample databases and their licences

    The compose file's samples service downloads each sample from a pinned URL and checks its SHA-256. Nothing is committed to the repository, so we never redistribute the files. If we ever vendor one, its licence file goes beside it.

    Sample Files Source Licence What we must do
    Pagila pagila-schema.sql, pagila-insert-data.sql github.com/devrimgunduz/pagila PostgreSQL License (copyright Devrim Gündüz) Keep the notice if the files are ever copied
    Sakila sakila-schema.sql, sakila-data.sql downloads.mysql.com (sakila-db.tar.gz) New BSD (stated on the Sakila licence page) Keep the notice if copied
    AdventureWorksLT 2022 AdventureWorksLT2022.bak github.com/microsoft/sql-server-samples, release adventureworks MIT (the repository's licence) Keep the notice if copied

    The server images have their own terms. The SQL Server image runs the free Developer edition, which needs ACCEPT_EULA=Y and is licensed for development and testing, which is all we do with it. The PostgreSQL and MySQL images are used as they are.

    The generated wide schema

    testbed/wide_schema.py --dialect postgres|mysql|tsql --seed 7 writes one SQL file. The same seed always gives the same schema. It has:

    Feature Count What it tests
    Schemas 20 (sales_01 ... ops_20, plus audit) IndexScope include and exclude, policy globs
    Tables 1,200, with 5 to 30 columns each Reflecting once, catalog-only indexing, retrieval at scale
    Views 2 per schema Views are indexed
    Odd column types boolean, uuid, json, binary, xml or array where the server has it Type-aware profiling never aborts
    Comments on 30% of tables and columns Descriptions come from the database
    Foreign keys within each schema Join paths
    Mixed-case names 10 tables, such as "CustomerAccounts" Quoting
    Rows 3 tables with 1,000,000 rows, 50 with 1,000, the rest empty Row estimates, max_profile_rows

    The big tables are filled on the server with a series function (generate_series, a recursive CTE, or a numbers table), so the file stays small. That SQL lives in the test bed, which is test code, not engine code.

    The compose file

    docker compose -f testbed/docker-compose.yml up -d --wait starts and loads everything. Loading happens once per data volume, so a second up is quick.

    Service Image What it does
    samples python:3.12-slim One-shot. Downloads the pinned samples, checks them, runs wide_schema.py for the three dialects, and writes the files into the samples volume. Skips what is already there.
    postgres postgres:16 Starts after samples. Its first start runs Pagila and the wide schema from /docker-entrypoint-initdb.d, the image's own init mechanism.
    mysql mysql:8.0 The same, with Sakila. The image's init uses the mysql client, which handles DELIMITER blocks.
    mssql mcr.microsoft.com/mssql/server:2022-latest Starts the server.
    mssql-init the same image (it ships sqlcmd) After mssql starts. Restores AdventureWorksLT from the .bak, loads the wide schema, and creates the test logins. Skips each step whose database already exists. Then it idles, healthy, instead of exiting: nothing waits for it to complete, and --wait fails on an exited container, which a skipping second up would otherwise produce.

    Every service has a healthcheck, so --wait returns only when every server is loaded. Each server also gets a login nl2sql_reader with read grants on its sample database only; the conformance kit uses it for the permission stage of test_connection.

    The file reads four variables. The bind address has a default; the passwords do not, so no password is written in the repository:

    Variable Default On the GCP VM
    TESTBED_BIND 127.0.0.1 0.0.0.0 (the firewall admits only IAP, see below)
    TESTBED_POSTGRES_PASSWORD none: required; testbed/passwords.py makes random ones, and CI makes new ones per run from Secret Manager
    TESTBED_MYSQL_PASSWORD none: required; testbed/passwords.py makes random ones, and CI makes new ones per run from Secret Manager
    TESTBED_MSSQL_PASSWORD none: required; testbed/passwords.py makes random ones, and CI makes new ones per run from Secret Manager
    Service Published port User
    postgres 15432 postgres
    mysql 13306 root
    mssql 11433 sa

    The ports avoid a clash with a database already installed locally.

    Local use

    python testbed/passwords.py > testbed/.env               # once

    CI: the realdb workflow

    A new workflow, .github/workflows/realdb.yml, with three jobs (owner decision 2):

    Job Runs What it does
    changes always Works out whether the pull request touches database-facing code (the paths below)
    realdb on a pull request when changes says so; nightly on main (schedule); on demand (workflow_dispatch), which is run before every release docker compose ... up -d --wait on the runner, installs Microsoft's msodbcsql18 for pyodbc, installs packages/nl2sql[postgres,mysql,mssql,duckdb], then pytest -m realdb with REALDB=compose and REALDB_REQUIRED=1
    realdb-gate always (if: always()), after the other two Passes when realdb passed or was skipped because nothing database-facing changed; fails when it failed or was cancelled. This is the required check, so a skipped job is an honest pass and never mistaken for one that ran.

    The paths that make realdb run:

    packages/sdk/**
packages/nl2sql/src/nl2sql/adapters/**
packages/nl2sql/src/nl2sql/indexing/**
packages/nl2sql/src/nl2sql/storage/**        (and schema/** until S3 moves it)
packages/nl2sql/tests/realdb/**
testbed/**
.github/workflows/realdb.yml

    REALDB_REQUIRED=1 turns a skipped realdb test into a failure: a green run that skipped the real databases proves nothing. The unit job in test.yml changes to pytest -m "not integration and not realdb". The containers run on GitHub's runners; no cloud credentials are involved.

    The realdb marker and fixtures

    pytest.ini registers the marker:

    realdb: needs a real PostgreSQL, MySQL or SQL Server (the test bed). Start
    testbed/docker-compose.yml and set REALDB=compose, or run it through
    scripts/testbed.py for the GCP VM.

    The fixtures live in packages/nl2sql/tests/realdb/conftest.py:

    Variable Meaning
    REALDB=compose The compose servers on 127.0.0.1, at the published ports, with the passwords in TESTBED_*_PASSWORD
    REALDB_POSTGRES, REALDB_MYSQL, REALDB_MSSQL A URL for one server, such as postgresql://postgres:<password>@127.0.0.1:15432/, with the password percent-encoded. It wins over REALDB=compose. scripts/testbed.py run sets these.
    REALDB_REQUIRED=1 A missing server is a failure, not a skip 
    @pytest.fixture(params=["postgres", "mysql", "mssql"])
def server(request) -> RealServer: ...            # skips loudly, or fails under REALDB_REQUIRED

def datasource(server, database="pagila", **index) -> Datasource:
    """A Datasource for one test-bed database, built from the server's URL."""

@pytest.fixture
def engine_on(server, tmp_path) -> Callable[..., NL2SQL]: ...   # an engine on that server, fake LLM

    The skip message names the fix: "realdb: no PostgreSQL. Run docker compose -f testbed/docker-compose.yml up -d --wait and set REALDB=compose, or run python scripts/testbed.py run -- pytest -m realdb."

    Test code may name dialects and use SQLAlchemy directly. The boundary tests cover packages/*/src, not the tests.

    The GCP VM

    One small VM, nl2sql-testbed in nl2sql-testbed-261014 (zone us-central1-a), runs the same compose file (owner decision 3). It is started for a session and stopped after it.

    Setting Value
    Machine e2-standard-2 (2 vCPU, 8 GB: SQL Server alone wants 2 GB)
    Image Debian 12, with Docker and the compose plugin installed once by its startup script
    Disk 30 GB standard persistent disk: the images and the data volumes, kept while stopped, so a later session skips the load
    External IP Ephemeral only, for outbound traffic (image pulls, sample downloads). It is released, and free, while the VM is stopped.
    Inbound No public database port. The VM sits in its own VPC, nl2sql-testbed, so the default network's open SSH and RDP rules do not apply, and one firewall rule admits TCP 22, 15432, 13306 and 11433 from IAP's range 35.235.240.0/20 only.
    Access gcloud compute start-iap-tunnel, which forwards localhost:15432, 13306 and 11433 on the caller's machine to the VM
    Passwords Secret Manager: the existing testbed-postgres-root-password, testbed-mysql-root-password and testbed-mssql-root-password. Never in the repository.
    Bucket gs://nl2sql-testbed-261014-samples is not needed: the VM downloads the samples itself, once

    There are no GitHub-to-GCP credentials. The owner, or an agent the owner asks, runs the VM by hand.

    scripts/testbed.py is Python, not a shell script, because the owner works on Windows and CI runs Linux. It calls gcloud (found with shutil.which, so gcloud.cmd works) and never writes its own process's environment.

    Command What it does
    up Starts the VM (gcloud compute instances start). Copies testbed/ to it (gcloud compute scp --tunnel-through-iap). Runs docker compose up -d --wait on it over gcloud compute ssh --tunnel-through-iap, with TESTBED_BIND=0.0.0.0 and the three passwords from Secret Manager passed on that command's environment only (they travel on its stdin, never on a command line). Then opens the three IAP tunnels in the background and waits until each local port answers.
    run -- <cmd> up, then runs <cmd> with REALDB_POSTGRES, REALDB_MYSQL and REALDB_MSSQL (pointing at the local tunnel ports) in the child's environment only, then closes the tunnels and stops the VM in a finally: also on Ctrl-C, a failing command or a failed up. It exits with the command's code.
    down Closes any tunnels it opened, runs docker compose stop on the VM (bounded; a failure is reported, not fatal) so SQL Server shuts down cleanly, then stops the VM. Safe to run again.
    status The VM's state, how long it has been running, and whether the tunnels are open. Never a password.

    Passwords are read with gcloud secrets versions access latest into memory, and are never written to a file or printed.

    The nightly backstop. If testbed.py is killed hard, or the VM is started by hand, it would keep billing. Stopping a stopped VM does nothing, so the job needs no logic, and one job is inside Cloud Scheduler's free tier.

    4. Storage: four stores

    Built: the interfaces, config and registry kind (S1)

    nl2sql_sdk.stores holds the four protocols with Entry, Hit, Filter and BuildPointer; StoreConfig and the four Storage sub-blocks are in nl2sql/config/models.py; the store registry kind (add_store, @registry.store, group nl2sql.stores) and the slot check are in nl2sql/registry.py and nl2sql/storage/__init__.py. The built-ins, nl2sql/storage/{chroma,sqlite,files,local}.py, are thin wrappers that build today's VectorStore, SqliteSchemaStore and ArtifactStore and hold the traces folder; Runtime.index, .state, .traces and .results are built through the registry. Building it settled these details:

    • IndexStore.query returns Hit (id, text, metadata, distance, and vector only when with_vectors), which the sketch below used without defining.
    • Until S2 to S4 move the engine onto each interface, the engine reads a slot only through its built-in store, and a plugin store in that slot is a ConfigError at storage.<slot> rather than silently unused.
    • max_age_days arrives with retention in S4; until then files and local take no keys.

    Built: the index store and the pointer as the commit (S2)

    nl2sql/storage/chroma.py is the chroma index store on Chroma's public client API, one collection per namespace, with each datasource's BuildPointer in the collection's metadata. The engine embeds and ranks: nl2sql/indexing/retrieval.py holds the Retriever (MMR in numpy over the vectors query returns) and namespace_for; indexing/vector_store.py, retrieval_trace.py, indexing/embeddings.py (the local embedder moved to embeddings/local.py), staging, full, switch_guard, EmbeddingModelMismatchError, get_latest_snapshot/get_latest_version and settings.schema.version_mismatch are deleted. Runtime.vector_store is a Retriever on the live pointers, Runtime.pin_index() pins them for a run (run_with_graph calls it), and the index slot takes any IndexStore. engine.index.prune() and nl2sql index prune are added. Building it settled these details:

    • Entry.metadata holds scalars only, so a relationship entry stores from_columns and to_columns comma-joined and the retriever splits them; empty values are left out.
    • The local embedder uses chromadb's bundled ONNX model function, so embeddings/local.py is the one exception to "only nl2sql/storage/ imports chromadb". langchain-chroma is no longer a dependency.
    • Health keeps index_version per datasource (the pointer's schema version, which the playground shows) and drops snapshot_version; stale now means a datasource without a live build, or whose snapshot is gone.
    • The chroma store opens index/ on the first write; reads of a missing folder or namespace create nothing.
    • Snapshot immutability and keep_snapshots (so eviction never removes a pointed version) are S3's: until then settings.schema.max_versions still evicts the oldest versions, and an unchanged structure still refreshes its stored metadata in place.

    Built: the trace and result stores, and retention (S4)

    nl2sql/storage/files.py is the files TraceStore and nl2sql/storage/local.py the local ResultStore, each with max_age_days (14 and 7, at least 1) and purge. The run trace is written through Runtime.traces, engine.traces.get reads through it, and ArtifactStore(results, path_template) writes Parquet and the manifest through Runtime.results; ArtifactStoreConfig and Runtime.traces_dir are deleted, and the traces and results slots take any store. engine.storage.info() and purge(), nl2sql storage purge and the API's startup and daily purge are added. No S3 or ADLS store is built in; storage/artifact-store.md has an S3 example. Building it settled these details:

    • ArtifactRef.uri is the result's key in the results store (<tenant_id>/<request_id>/<sub_query_id>.parquet), not a file path, and ArtifactRef.backend is deleted.
    • Reading a result: when ResultStore.open returns a local file, as local does, polars scans the file in place; any other stream is read into memory first, since a scan outlives the call that opened it.
    • purge() purges a store that has a max_age_days attribute and leaves one without it alone; it returns the counts per slot purged.
    • QueryResult.trace_path is the file the files store wrote, and None with another trace store; trace_id always names the trace.
    • nl2sql trace show <id> reads through engine.traces.get. Runtime.stores (StorePaths) stays for the state store's callers until S3.

    Built: the state store, migrations and the lock (S3)

    nl2sql/storage/sqlite.py is the sqlite state store: immutable snapshots (a trigger refuses any UPDATE), the plan cache, feedback, nl2sql_meta migrations (1 adopts 0.5's three tables, 2 adds the later feedback columns, 3 adds the trigger and the locks table) and the lease. schema/sqlite_store.py, schema/in_memory_store.py, schema/store.py, schema/protocol.py (the fingerprint moved to schema/fingerprint.py) and feedback/store.py are deleted; Runtime.schema_store is gone and the engine reads Runtime.state through StateStore, so the state slot takes any state store. The runtime calls migrate() when it opens the stores; the store opens its file on first use. health.py, nl2sql cache clear (through the new engine.clear_plan_cache()) and nl2sql curated proposals export (through engine.feedback.list()) go through the engine. Building it settled these details:

    • StateStore.list_versions(datasource_id), newest first, is added: the engine needs it to keep "the newest max_versions".
    • put_snapshot returns the stored version when the contract and metadata are identical, and stores a new version otherwise, so a re-index whose statistics changed gets a new version and a cold plan cache for that datasource (the cache is already keyed on the run date).
    • After a build, keep is every version a pointer names in any namespace, the version the build replaced (runs in flight may have pinned it, as with builds), and the newest max_versions.
    • engine.index.build() holds the index lock with a one-hour lease; a build started while it is held fails every datasource at once with the holder's expiry. A store's lock() raises when the lease is held.
    • The engine builds the feedback row (nl2sql.feedback.rated_row) and the store keeps it as given, so add_feedback needs no rating rules.
    • With every slot read through its interface, the runtime's "built-in only" slot check, Runtime.stores (StorePaths) and the CLI's store_paths are deleted.

    Design notes:

    • The engine embeds. Today Chroma's LangChain wrapper embeds documents itself. In 0.6 the engine embeds with its own embedder and hands the store vectors, so a store never depends on LangChain, and MMR runs in the engine on the vectors query returns.
    • No staging or rename in the interface. A rebuild writes a new build beside the live one and switches a pointer, so no backend has to rename anything.
    • The filter is small on purpose. eq, ne and in (combined with "and") are all the engine uses today. Each backend translates them.
    • ResultStore stores bytes. The engine still writes Parquet and the manifest; the store only puts and gets them. A remote store (S3, ADLS) then needs four methods and no Polars knowledge.
    • The lock is a lease in the state store: in SQLite, a locks row taken in a BEGIN IMMEDIATE transaction, with an expiry so a crashed holder cannot block forever. It makes nl2sql index safe to run while nl2sql-api serves the same storage.path, and needs no new dependency.

    The build pointer is the commit (bug B5)

    The bug. Indexing registers the schema snapshot in the state store before it writes the index (indexing/orchestrator.py), and the resolver, retriever, curated matcher and datasources.schema() read the state store's latest snapshot. If the index build fails, the "latest" snapshot describes a schema the live index was never built from. Today this only produces a warning (settings.schema.version_mismatch).

    The fix. A snapshot is an immutable row keyed by schema_version. The index's BuildPointer records the schema_version the build was made from, and every reader resolves "live" through the pointer. Switching the pointer is the commit.

    sequenceDiagram
  participant I as Indexing
  participant S as State store
  participant X as Index store
  participant R as A run
  I->>S: put_snapshot(snapshot) returns v42 (nothing reads it yet)
  I->>X: add(entries tagged build b7)
  I->>X: set_pointers(sales to build b7 and schema v42)
  Note over X: the commit
  R->>X: pointers() once, at the start of the run
  R->>S: get_snapshot(sales, v42)
  R->>X: query(where build_id = b7)
    • A failed build leaves an unreferenced snapshot and entries that no pointer names. The next build of that datasource deletes them.
    • get_latest_snapshot and get_latest_version are deleted, so no reader can ask the wrong question. settings.schema.version_mismatch is deleted, because the mismatch can no longer happen.
    • keep_snapshots keeps every version a pointer names, plus the newest settings.schema.max_versions.
    • It works for any pair of backends (Chroma and SQLite today, pgvector and PostgreSQL later) without a transaction across the two.

    A run pins the pointers

    A run reads pointers() once, when it starts, the way it already pins its LLM set. Every step of the run uses that build and that schema version. To make that safe, a new build deletes only the builds before the previous one, so an in-flight run never loses its entries. That replaces switch_guard and the playground's RunGate for index switches.

    One namespace per embedding model

    The index namespace is nl2sql__<model slug>__<dimension>, for example nl2sql__local-all-minilm-l6-v2__384. The slug and dimension come from the embedder (see section 5).

    • Changing the embedding model opens a new, empty namespace. check() reports the index as missing for the new model, with "run nl2sql index". EmbeddingModelMismatchError and the dimension check are deleted.
    • Switching back to an earlier model finds its namespace still built.
    • engine.index.prune() and nl2sql index prune drop every namespace except the current one, including 0.5's nl2sql_store collection, which 0.6 never reads.
    • A full rebuild no longer needs a staging collection: index.build() with no ids builds every datasource in the current namespace. The full argument, create_staging, promote and discard are deleted.

    Migrations and retention

    • Migrations. The SQLite state store keeps a nl2sql_meta table and applies numbered migrations at startup. Migration 1 creates 0.5's three tables if they do not exist, so a 0.5 state.db is adopted as it is. The feedback store's ad-hoc ALTER TABLE statements move into migrations.
    • Retention. files traces and local results take max_age_days (defaults 14 and 7). engine.storage.purge() deletes what is older and returns the counts. nl2sql storage purge calls it, and nl2sql-api calls it at startup and once a day. Feedback and snapshots have no age limit: feedback is cleared by hand, and snapshots by keep_snapshots.

    Structured output, and parse-and-retry

    Every structured call already goes through one function, structured() in llm/wires/__init__.py. Phase 2 changes it:

    1. Ask with the agent's structured_output method. For json_mode, the schema is added to the prompt, since JSON mode alone does not carry it.
    2. If the answer does not parse (OutputParserException, a pydantic ValidationError, no tool call, or None), ask again, up to parse_retries times. Each retry adds the model's answer and the validation errors to the messages: "Your answer did not match the schema: steps[0].op: field required. Answer again with only PlanModel."
    3. If it still fails, raise StructuredOutputError(agent, schema, attempts). provider_error() maps it to a new ErrorCode.MODEL_OUTPUT_INVALID, whose message names the agent and suggests another structured_output or a stronger model.

    The method is not switched automatically: the agent's setting is what runs. Retries are counted in the run's trace and in token usage. A streamed answer that fails to parse is retried without streaming.

    Case Matching ignores case, so a deny cannot be dodged by Orders against orders.
    Within a role Deny beats allow.
    Across roles A caller may read a table if some role allows it and that same role does not deny it. That keeps 0.5's union.
    Datasource access Implied: a role reaches a datasource when any of its allow patterns can match inside it.
    Unknown datasources A pattern naming a datasource that is not configured is a policies.validate() problem, not a startup error, because datasources can be added at runtime.

    Denied tables are hidden from the planner

    The owner decided (D7) that denied tables are hidden by default. In 0.5 the planner sees every table's name, columns and keys ("structure yes, data no"). In 0.6 the retriever filters entries through the Scope before it takes the top k, fetching more candidates when needed, so a schema with many denied tables still fills the prompt with readable ones.

    What the user sees changes: a question that needs only denied tables gets "no data for that question" from the planner rather than a refusal. A plan that names a hidden table anyway is still refused by the validator. With refusal_names_tables: true the refusal names the table, for debugging.

    ConnectionModel and the generated form

    Each built-in declares its model publicly. For example:

    class PostgresConnection(SQLAlchemyConnection):     # SQLAlchemyConnection adds `pool`
    host: str = Field(title="Host", examples=["db.internal"])
    port: int = Field(5432, title="Port")
    database: str = Field(title="Database")
    user: str = Field(title="User")
    password: SecretStr = Field(title="Password")
    sslmode: Literal["disable", "prefer", "require", "verify-full"] = Field(
        "prefer", json_schema_extra={"group": "advanced"})
    • Strict. extra="forbid": hostname: is now an error with "did you mean 'host'", where 0.5 silently ignored it (bug B18).
    • Validated at build. The engine resolves the references in connection, then validates against the adapter's model. Python callers may pass a dict or a model instance: Datasource(connection=PostgresConnection(...)).
    • The form. connection_model.model_json_schema() is the form. A SecretStr field is "format": "password", "writeOnly": true, which a form renders as a password input. A field in the advanced group is folded away. A new adapter gets a form for nothing.
    • Pool. SQLAlchemyConnection adds pool: {size: 5, max_overflow: 0, timeout_s: 30, recycle_s: 1800}. With no overflow, the pool size is also the cap on concurrent queries against that database, so NL2SQL cannot overload a production server.

    IndexScope: what gets indexed

    # datasources/sales.yaml
type: postgres
connection: { host: db.internal, database: sales, user: nl2sql, password: "${env:SALES_DB_PASSWORD}" }
index:
  include_schemas: [public, reporting]
  exclude_tables: ["*.*_audit", "public.tmp_*"]
  exclude_columns: ["public.customers.email"]
  profile: stats
  sample_values: false
    Field Default Meaning
    include_schemas every schema except the adapter's system schemas Globs
    exclude_schemas none Globs, applied after include
    include_tables, exclude_tables all, none schema.table globs
    exclude_columns none schema.table.column globs: the column is not indexed or profiled. This is not access control; deny_columns is a later policy step.
    profile stats catalog: names, types, keys, comments and catalog row estimates, with no query against table data. stats: also each column's null share, distinct count and min/max.
    sample_values false Store each text column's values (all of them when 50 or fewer distinct, otherwise the five most frequent). Off by default (owner decision D18): values reach the index, prompts and the provider. NL2SQL.demo() and init --demo turn it on.
    max_profile_rows 1,000,000 A table estimated above this gets catalog profiling and an IndexIssue saying so

    The filter runs before any per-table query, so an excluded schema costs nothing. The scope is part of the snapshot's fingerprint, so changing it makes a new schema_version.

    Profiling and row estimates

    The SQLAlchemy base changes how it reads a schema:

    • Reflect once. inspector.get_multi_columns, get_multi_pk_constraint and get_multi_foreign_keys per schema, instead of reflecting the whole database twice table by table. The wide schema measures it: the target is a catalog snapshot of 1,200 PostgreSQL tables in under 60 seconds in CI.
    • Catalog row estimates. An overridable row_estimates(conn, schema) -> dict[str, int] | None: PostgreSQL pg_class.reltuples, MySQL information_schema.tables.table_rows, SQL Server sys.partitions, DuckDB duckdb_tables().estimated_size. SQLite returns None, and gets COUNT(*) under profile: stats. Nothing counts every row of every table any more.
    • Type-aware statistics. An overridable column_profile(sa_type) -> ColumnProfile(min_max, distinct, values). No MIN/MAX on boolean, uuid, json, binary, xml or arrays; values only for text and only with sample_values. This makes 0.4.1's skip list a public rule.
    • Isolation. Each column's statistics query is isolated as today (a rollback after a failure), and a failure becomes an IndexIssue instead of a log line, so index.build() can report it.

    Read-only and timeouts, honestly

    Each adapter does its session setup in one place, session_setup(dbapi_conn), run on every new pooled connection. A capability is declared only when the conformance kit proves it on a real server.

    Adapter Read-only Timeout ENFORCES_READ_ONLY ENFORCES_TIMEOUT
    PostgreSQL SET default_transaction_read_only = on SET statement_timeout yes yes
    MySQL SET SESSION TRANSACTION READ ONLY SET SESSION MAX_EXECUTION_TIME (applies to SELECT, which is all the engine runs) yes yes
    SQL Server none at session level: ApplicationIntent=ReadOnly only routes to a readable replica pyodbc's query timeout (the client cancels) no yes
    DuckDB read_only=True on the connection interrupt after the deadline (0.4.1) yes yes
    SQLite mode=ro always, not only with options.read_only a progress handler that stops a statement after the deadline (today it is only a lock wait, bug B20) yes yes

    There is no read_only setting: the engine never writes, so every adapter always makes its session read-only when it can. When it cannot (SQL Server), engine.check() adds a warning to that datasource's status: "sales (mssql): this adapter cannot make the session read-only. Connect with a login that has only db_datareader." The typed plan and the validator still block every write. This is owner decision 4.

Engine events go on the runtime's bus (ctx.bus), since an index build, a datasource check and a purge run outside any question: rebuild_index publishes index.started and index.failed, IndexingOrchestrator publishes one index.column_failed per IndexIssue (the issue only, never a sample value) and index.swapped from _commit, Runtime.check_datasource and try_datasource publish datasource.failed, and engine.storage.purge() publishes retention.purged with the counts it returns.
