    Wave D: the apps (API v1, web app, Compose, terminal app) (design)

    Status: design

    This page is the design for Wave D of the product redesign, the last wave, which ships as the release after 0.9. Nothing on it is built yet. Each pull request in the PR plan adds a "Built" note to the sections it builds, as the earlier phases and waves do. Phase 1 is Configuration v2 and the extension registry; Phase 2 is Phase 2: test bed, storage, providers, policies and adapter SDK v2; Wave A (0.7: events, observers, hooks, approval, evals, routing, drift, sanity warnings, MCP over stdio) and Wave B (0.8: glossary and knowledge, the profiler and review queue, clarification, plan-to-English, the cost guard, corrections) are designed on their own pages. Wave C (0.9: conversations and chat tools, ChartSpec, dashboards, the launchpad, API keys, MCP over HTTP) is designed in architecture/wave_c.md, not merged when this page was written; this page follows its amended version. Wave D renders what the three waves build. Where it needs something they do not provide, the gap is listed in Needs from Waves A to C as a facade method, not designed around.

    Wave C was revised on 2026-10-28; this page has not been updated to match

    Wave C now has a model-led chat (the model calls tools in a bounded loop; conversation.step replaces conversation.rewritten), dashboards that are artifacts pinned whole (several sub-queries per chart; needs_fixing replaces stale; no single-tile pin), workspaces, manual dashboard edits with chat parity, refresh with stored results and schedules, and one access rule for every entry point. Wave D's dashboard and chat routes, its Dashboards and Chat pages, D224 and the job and fixture tables still describe the first draft and need a pass. The rows below that name a changed Wave C item are corrected; the rest are listed here, not rewritten: the Chat tool buttons (Pin becomes pinning the whole dashboard), POST /dashboards/pin and the tile routes, the Dashboards page (workspaces, arrange, edit, schedule, "refreshed 2 h ago", needs_fixing), and the dashboard job.

    The owner set them for the redesign, and they rank above everything below:

    • The package is the product; the playground only demonstrates it. The web app talks only to nl2sql-api's public /api/v1 routes. The terminal app talks only to the Python facade. Neither holds feature logic: a chart is chosen by engine.results.chart, a dashboard by engine.dashboards.generate, a follow-up by engine.conversations.ask. Every gap this page found is a facade method plus a route, listed explicitly.
    • No active users: correct, not compatible. Routes are renamed where their names are wrong, the playground's private server is deleted, and nl2sql demo keeps no flag whose behaviour is gone. No aliases.
    • Never over-engineer. One process, one worker, jobs in memory, one Docker image, one Compose service, plain React and plain CSS. The apps expose what Waves A to C build and nothing they cut. The cut list is part of the design.
    • Both apps have a demo mode and a your-data mode. Demo mode is the sample databases with recorded answers and no key; your-data mode is the caller's nl2sql.yaml.
    • The UI must not look AI-generated. The playground's "Porcelain" design system (web/playground/src/styles.css: its tokens, type scale, the run spine, the raised card, the 44px controls) is the baseline for every new page. No component library, no gradient, no icon font.

    Decisions

    The owner was asleep when this design was written and asked that its recommendations be used, each marked for confirmation. Wave A uses D9 to D35, Wave B D36 to D61 and Wave C D100 to D130, so Wave D starts at D200. After an independent review several were amended; those are marked so. The final redesign's decisions D13 to D16 are cited by the brief for this wave; their numbers collide with Wave A's, so this page calls them final-design D13 to D16 and records how each is applied.

    # Decision Status Where
    D200 The apps hold serving state only. nl2sql-api may keep the job queue, hosted-demo limits and sessions; everything a user would call a feature is a facade method. nl2sql_api imports only the top-level nl2sql, and the web app calls only /api/v1 routes listed in the committed openapi.json. Both are tests. decided overnight, owner to confirm Principles, Boundaries
    D201 One route convention, applied to the old routes too: plural nouns (/datasources, /conversations, /results), ids in the path, an action on a collection or a resource as a verb sub-path (/proposals/accept), long work as POST /jobs/{kind}. /datasource, /index/{id}, /index-all, /index/status, /llm/{agent} and /query/{request_id}/results/... are renamed or folded with no alias. decided overnight, amended after review, owner to confirm Conventions
    D202 One error envelope, and only the facade's own exceptions are mapped. {"error": {"code", "message", "fix", "details"}} for every non-2xx response. The facade's named exceptions share one base, nl2sql.NL2SQLError (code, message, fix, status); the API maps that base and nothing else. Any other exception, a built-in ValueError, KeyError or PermissionError included, is a 500 naming a request id, never its text. A pipeline outcome stays a 200 with the QueryResult. decided overnight, amended after review, owner to confirm Errors
    D203 Every request resolves one full UserContext (user_id, tenant_id, roles) from one configured source, api.auth: api_keys (Wave C's bearer keys), proxy (user, tenant and role headers, trusted only from proxy.trusted_from), static (one role) or none. Anonymous browser sessions exist only inside serve --demo --hosted, never as a config value. trust_body_role, role_header and role are deleted. decided overnight, amended after review, owner to confirm Identity
    D204 Results and traces are bound to the user who asked (bug B13) in the engine. Results were built early by Wave C's C-W2, with a required user_context and no operator path (see the B13 note); what follows is for traces. A run records its asker's (tenant_id, user_id); traces.get with a user_context answers only that asker, and another user's run is "not found". user_context=None is the trusted in-process operator for traces, as Wave A's D24 and Wave C's keys treat it, so nl2sql trace reads any run. The API, MCP and the terminal app always pass the caller, which a boundary test checks. Every new method this wave adds requires the caller and fails closed (Wave C's D130). decided overnight, amended after review, owner to confirm Results bound to the user
    D205 Final-design D15, applied safely: with api.auth: none, nl2sql-api refuses to start unless it binds a loopback host, as Wave C's MCP does without keys. It then answers only requests whose Host is localhost, 127.0.0.1 or [::1] (with its port) and refuses any request carrying Forwarded or X-Forwarded-For, so neither a same-host proxy nor a DNS-rebinding page passes for the operator. Such a request is the local operator, with the admin roles. Compose ships with auth: api_keys. decided overnight, amended after review, owner to confirm Identity
    D206 Jobs run in process, on one worker thread, in memory. A job is one facade call (index, profile, eval, dashboard) with a progress callback; jobs run one at a time in submission order; each caller has at most one job queued or running; the last 100 are kept and lost on restart. nl2sql-api runs one Uvicorn worker. The durable queue is cut. decided overnight, amended after review, owner to confirm Jobs
    D207 Server-Sent Events carry Wave A's Event as is (event.sse()), through one helper that closes the facade's iterator when the client goes away (and cancels the token where the method takes one), with a heartbeat every 15 seconds. A job's event stream is an async generator, so a waiting browser holds no worker thread. decided overnight, amended after review, owner to confirm Streams
    D208 /ready is real, and its rule is the engine's: CheckReport.ready(keys_optional=) decides (every required datasource ready, every key resolves unless keys are optional, the index ok or stale). /ready answers status only to an anonymous caller and the report to an admin. The API now starts with a failed required datasource and reports not ready, instead of refusing to start. decided overnight, amended after review, owner to confirm Health and readiness
    D209 The replay provider is an LLM provider, provider: replay, answering through the normal LLM interface from a recordings file; a question it has no recording for ends with the error code REPLAY_MISS. The demo's local fake HTTP server and its error-string matching leave the demo path. nl2sql demo --record is removed; recording is scripts/record_demo_answers.py, run by the owner. decided overnight, owner to confirm The replay provider
    D210 A key typed into the web app stays in the browser tab and travels with each request as a per-call LLMOverride (llm_override= on the facade), in every mode. The web app never writes a key to disk. A model the caller chooses runs only on a key the caller sent: X-NL2SQL-Models is honoured only for providers the same request carries a key for, so a caller can never move a step onto the operator's account. Callers may bring a key only where api.request_llm: true; the demo sets it, the default is off. decided overnight, amended after review, owner to confirm Keys and models
    D211 Final-design D13, applied with one change. The web app ships inside nl2sql-api as package data, served by nl2sql-api serve. It adds no dependency to nl2sql-api, so there is no web extra there; instead the engine's demo extra becomes nl2sql-api, so pip install "nl2sql-engine[demo]" stays the one install line. nl2sql demo is a launcher that runs python -m nl2sql_api serve --demo in a child process; the engine never imports nl2sql_api. The playground server (nl2sql/cli/demo/) is deleted. decided overnight, amended after review, owner to confirm Serving
    D212 Final-design D14, applied through Wave C's writer: Connect's Save calls Wave C's datasources.save(id, *, by, env_file), which writes datasources/<id>.yaml, with env_file true only for the fresh local install (Wave C's D122). No second save target, no overlay, no new switch. Saving is admin work, so it is off on the hosted demo; where the config is mounted read-only (Docker), save fails with its own message and the datasource stays registered in memory until restart, which the page says. decided overnight, amended after review, owner to confirm Saving a datasource
    D213 Final-design D16, applied: one Docker image, nl2sql-api, with all five adapters and Microsoft's ODBC driver for SQL Server. The driver and unixODBC are small beside the ONNX runtime and Chroma the image already carries, so slim and full images are not worth two tags. CI builds and tests linux/amd64; arm64 is published only once K1 has checked that msodbcsql18 exists for Debian 12 on arm64. The image job records the size; a split is reconsidered only if the ODBC layers pass 15% of it. decided overnight, amended after review, owner to confirm Docker image
    D214 Charts are drawn by our own SVG renderer from ChartSpec (four kinds), in Porcelain's tokens; Vega is not bundled, and the Vega-Lite export is a download. Mermaid is loaded on the first diagram as its own chunk (about 2 to 3 MB of the nl2sql-api wheel, recorded by the web job). The single-file build is dropped. decided overnight, amended after review, owner to confirm Charts and diagrams
    D215 Approval grants are stored by the engine (engine.approvals), amending Wave A's D10 and D24 and Wave C's D107. Over HTTP the approver and the asker are two callers at different times: the asker cannot prove a grant, and the approver must not run the question as the asker, so the approver grants a request by id and the asker's re-run names the id. A grant is reusable until it expires (24 hours), as an Approval is. decided overnight, amended after review, owner to confirm Approvals
    D216 One React app, in web/app (renamed from web/playground): the existing Vite and React 18 setup, a hash router, plain JavaScript, Porcelain's CSS split per area, the API client split per area. No TypeScript, no state library, no component library. decided overnight, amended after review, owner to confirm The web app

    3. The API: /api/v1 at parity

    Route conventions

    Rule Detail
    Prefix Everything under /api/v1; the web page and its assets at /.
    Nouns Plural collections, ids in the path: GET /conversations/{id}. An action is a verb sub-path on the resource it acts on: POST /approvals/{id}/grant, POST /proposals/accept (the facade takes a list of ids).
    Long work POST /jobs/{kind} returns 202 and the job; GET /jobs/{id} and GET /jobs/{id}/events follow it (Jobs). No route blocks for longer than a question.
    Streams A route that streams a run ends in /stream and answers text/event-stream (Streams).
    Bodies Request models are pydantic, strict (extra="forbid"), declared beside their router. Responses are the facade's own models (QueryResult, Conversation, Dashboard, Proposal, ...), served as they are, so the HTTP shape cannot drift from the package's.
    The caller Every handler that calls an owned, scoped or privileged facade method passes the request's UserContext as user_context= or, for an admin write, by=.
    Sync handlers A handler that calls the engine is def, so Starlette runs it in its thread pool, as routes/query.py does today.
    No services layer nl2sql_api/services/ and dependencies.py are deleted: each wrapper was one line over a facade call. A router calls the facade directly.
    OpenAPI Every route has a summary, its request and response models and its error statuses. packages/api/openapi.json is committed; test_openapi_snapshot_is_current fails when it is stale and prints the command that rewrites it.

    The error envelope

    # nl2sql_api/errors.py
class ApiError(BaseModel):
    code: str                     # an NL2SQLError's code, or NOT_FOUND, INVALID_REQUEST,
                                  # UNAUTHENTICATED, FORBIDDEN, CONFLICT, LIMIT_REACHED, NOT_READY, INTERNAL
    message: str                  # one sentence a person can act on
    fix: str | None = None
    details: list[dict] = []      # 422: one entry per problem, {"loc": [...], "msg": ...}; never a value
    request_id: str | None = None # 500 only: the id in the server log

class ErrorBody(BaseModel):
    error: ApiError

    One base class (D202). The engine gains nl2sql.NL2SQLError(Exception) with code, message, fix and status (the HTTP status it means: 404, 409, 422 or 403).     Approvals over REST

    Wave A's approval holds nothing: the app that asked keeps the ApprovalRequest, and the approver's Approval names who approved. In process that works because one program sees both people. Over HTTP the approver and the asker are two callers, at different times, on different connections: the asker's request cannot prove that someone else approved, and the approver must not re-run the question as the asker (Wave A binds the run to the asker).
