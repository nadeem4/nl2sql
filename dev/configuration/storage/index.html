    Storage

    The storage section of nl2sql.yaml says where the engine keeps its data, and which store keeps each part of it. Only path is required:

    # storage.yaml
path: .nl2sql          # or "${env:NL2SQL_DATA_DIR}" in a container

    A relative path is relative to nl2sql.yaml in a file, and to the working directory when the Config is built in code. nl2sql init writes .nl2sql and adds .nl2sql/ to .gitignore.

    Everything the engine writes lives under it:

    Under path What Was (0.4)
    index/ The vector index (Chroma). The collection name is an internal constant. VECTOR_STORE, VECTOR_STORE_COLLECTION
    state.db SQLite: schema snapshots, the plan cache and playground feedback. SCHEMA_STORE_PATH
    traces/ Run traces (settings.traces.mode). TRACE_DIR
    results/ Result files, <tenant_id>/<request_id>/<sub_query_id>.parquet. See Artifact Store. RESULT_ARTIFACT_BASE_URI

    The four stores

    Each part of that data has a slot, and each slot a store, named by type. Every sub-block is optional; left out, a slot uses its built-in store, so the section above is the same as:

    path: .nl2sql
index:   { type: chroma }    # <path>/index/
state:   { type: sqlite }    # <path>/state.db
traces:  { type: files }     # <path>/traces/
results: { type: local }     # <path>/results/
    Slot Built-in Holds
    index chroma The vector index
    state sqlite Schema snapshots, the plan cache, feedback
    traces files Run traces
    results local Result files

    A store's other keys are its own, checked by the store when the engine is built, so a misspelt key is an error. They may be ${provider:key} references, resolved through the secret providers when the store is built:

    index: { type: qdrant, url: "http://qdrant:6333", api_key: "${env:QDRANT_KEY}" }

    Store names share one entry point group, nl2sql.stores, so a name is unique across the four slots. A store in the wrong slot is refused with the stores installed for that slot: "'chroma' is an index store; results needs a results store. Installed: local."

    In code, a slot takes a StoreConfig or a store object, used as given:

    from nl2sql import Storage, StoreConfig

Storage(path=".nl2sql")
Storage(path=".nl2sql", traces=StoreConfig(type="files"))
Storage(path=".nl2sql", index=my_index_store)   # any object whose slot is "index"

    The store interfaces are in nl2sql_sdk.stores. A plugin registers a store in the nl2sql.stores entry point group, or in code with registry.add_store(name, cls).

    Built-ins only, for now

    0.6 moves the engine onto the four store interfaces one slot at a time. Until a slot's move lands, the engine reads that slot through its built-in store only, and refuses any other store there with a problem at storage.<slot>.

    Sharing

    Two engines with different paths share nothing. The commands that only read these stores (nl2sql cache clear, nl2sql feedback, nl2sql trace show) find them from the same config, so run them with the same --config.

    Results are local files. The S3 and ADLS result backends of 0.4 were removed; remote stores come back with the results-store interface in a later release.

    In a container, mount a volume and point the path at it:

    path: "${env:NL2SQL_DATA_DIR}"

    docker run -e NL2SQL_DATA_DIR=/data -v nl2sql-data:/data ...
