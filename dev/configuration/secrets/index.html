    Secrets Configuration

    The secrets section of nl2sql.yaml is optional. It lists secret providers that the rest of the config can reference as ${provider_id:key}. The env provider (${env:VAR}) is always there without it.

    # nl2sql.yaml
secrets: { file: secrets.yaml }

    # secrets.yaml
providers:
  - id: aws-main
    type: aws
    region_name: "us-east-1"

    providers may be omitted or left empty: both mean "no secret providers configured".

    Providers

    Each provider has:

    • id: unique provider ID used in secret references (e.g. ${aws-main:db_password})
    • type: aws, azure, hashicorp, or a provider a plugin registers. The id env is reserved for the built-in provider.

    Every other key is the provider's own setting:

    type Settings Extra to install
    aws region_name, profile_name, both optional (boto3's own lookup fills them in) nl2sql-engine[aws]
    azure vault_url (required), client_id, client_secret, tenant_id. Without all three credentials the provider signs in with DefaultAzureCredential. nl2sql-engine[azure]
    hashicorp url and token (both required), mount_point (default secret) nl2sql-engine[hashicorp]
    env none none 
    providers:
  - id: vault
    type: hashicorp
    url: "https://vault.internal:8200"
    token: "${env:VAULT_TOKEN}"

    The settings are strict. An unknown or misspelt key, or a missing required one, fails when the config loads, and the message names the key.

    A provider reads its settings from its entry only. It never falls back to an environment variable such as VAULT_ADDR, VAULT_TOKEN or AZURE_KEYVAULT_URL: when a value comes from the environment, write the field as an ${env:...} reference, as token does above.

    The HashiCorp key is the secret's path and, after a colon, the field: ${vault:apps/sales:password} reads the field password of apps/sales in the KV version 2 engine at mount_point. Without a colon it reads the field value.

    Each provider implements the SecretProvider interface from the SDK; see SDK reference → SecretProvider.

    Secret references

    Use ${provider_id:key} to resolve a secret from a provider, and ${env:VAR} to read an environment variable. A reference is the whole value. Every api_key and every value under a datasource's connection keep the reference until the component is built, so engine.config, logs and errors never hold the secret. Inside secrets: itself only ${env:...} is allowed: one provider cannot depend on another. See Configuration System → references.

    When a provider fails to start

    A provider in the secrets section that cannot start fails startup at once: building the engine raises a ConfigError naming secrets.providers[i] (the CLI, nl2sql-api and nl2sql doctor print it). The error names the provider and the reason:

    Secret provider 'vault' (type 'hashicorp') failed to start: Missing dependency 'hvac'.
Install 'nl2sql-engine[hashicorp]'. Fix or remove this entry in the secrets config.

    The usual reasons are the provider's extra not being installed (nl2sql-engine[aws], [azure], [hashicorp]), a ${env:VAR} credential whose variable is not set (the message names the variable), or the provider's own client refusing the config. Credentials are masked in the message.

    This is deliberate: every ${vault:...} reference depends on the provider, so starting without it only moves the error to the first lookup, where it reads as "Unknown secret provider ID". A config without a secrets section and the built-in env provider are unaffected. A datasource that fails to start, by contrast, leaves the others running: see Datasources → When a datasource fails to start.

    Secrets never print

    A credential written as a value never prints: repr, str, log lines and tracebacks of the config show ********** instead. A ${provider:key} reference is not a secret and is shown as written. This covers:

    • api_key in llm, in each of llm.agents, and in embeddings, including a key the demo gives the engine in memory (nl2sql demo --api-key, or one saved in the playground's settings panel): repr(engine.config) never shows it;
    • in the secrets section, every provider setting whose name contains password, secret, token or api_key (client_secret for Azure, token for HashiCorp); the URL and the other settings still show;
    • in a datasource's connection, every field whose name contains one of the same words;
    • the resolved key the LLM registry builds a client from (AgentConfig, a pydantic SecretStr), including model_dump(mode="json") and model_dump_json().

    The config's own fields stay plain strings, so the engine (and config.model_dump()) reads the real value; only printing masks it. A config built in code that fails validation never echoes its input either: the error names the field and the problem, not the value.

    The real value is read only where it is used: building the LLM or embeddings client, a database connection, the artifact store's storage options or a secret provider's client. nl2sql init never writes a key: a key belongs in the environment or the .env next to nl2sql.yaml. The demo and the playground's Settings page save a key to that .env only, with its real value.
